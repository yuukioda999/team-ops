# 007 デモモード:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断した点は ADR-0021 に記録した。

## 全体の流れ

```
[訪問者] ログイン画面 → 役割を選んで「デモとしてログイン」
   → API がデモチームを1つ作る(架空の代表・役員・コーチ・保護者・選手、承認待ちの申請、送信済み・予約中のお知らせ)
   → 選んだ役割のデモユーザーとしてログイン。画面上部に「デモ環境です。入力したデータは24時間後に削除されます」
   → 役割の切り替え:同じデモチームの別のデモユーザーとしてログインし直す
   → お知らせを送る → notify-relay → Mailpit(外には出ない) → 「送信されたメール」画面で自分のチームの分だけ見る
[定期処理] 作成から24時間を過ぎたデモチームを、ユーザー・メールの記録ごと消す
```

## いまあるもの

- 設定 `DEMO_MODE`(既定 false)と `RECIPIENTS_INVALID_ONLY`(作業環境は true)。API は .invalid 以外の宛先に送らない(005・006)、relay も同じ条件で拒否する(001)
- チームを消すと、名簿・お知らせ・既読・招待・監査ログは外部キーで一緒に消える
- チーム間の分離(`{team}` の解決とテナント分離のテスト)。デモチームも同じ仕組みで守れる(AC-007-06)

## いまないもの

- デモチームの作成・役割の切り替え・削除、デモの目印(チームとユーザー)
- デモ中に使えない操作の制限(マジックリンク、メールアドレス変更、チーム作成、招待からの参加)
- 送信されたメールを見る仕組み、サンプル CSV

## 判断した点(2026-11-08 小田がすべて推奨案で決定)

### 判断1. デモチームの作り方(spec の「テンプレートから複製」)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 架空のデータをコード(1つのクラス)に持ち、ログインのたびにそこからデモチームを作る。DB にテンプレートのチームは置かない |
| B | DB にテンプレートのチームを1つ置き、毎晩作り直す。ログインのたびに行をコピーする |

推奨の理由:名前・メールアドレスは暗号化とブラインドインデックス(ADR-0003)があり、メールアドレスはチームごとに変える(`保護者1@demo-{チームID}.invalid`)ので、B でも行をそのままコピーできず、作り直しが要る。A なら作り方が1か所で、テンプレートが古くなることもない。20人規模なら3秒以内(AC-007-02)に十分収まる。
**spec の変更が要る**:方式の「テンプレートから複製」「テンプレートの作り直し」と AC-007-19 の「テンプレートを作り直す」を、「架空のデータの定義から作る」に直す。

### 判断2. 削除の間隔

| 案 | 内容 |
|---|---|
| **A(推奨)** | 1時間ごとに、作成から24時間を過ぎたデモチームを消す |
| B | spec どおり毎晩1回 |

推奨の理由:毎晩1回だと、最長で約48時間残る。画面の「24時間後に削除されます」と合わない。1時間ごとなら24時間〜25時間で消える。
**spec の変更が要る**:方式と AC-007-07 の「毎晩」を「1時間ごと」に直す。

### 判断3. 「送信されたメール」の取り出し元(AC-007-12)

| 案 | 内容 |
|---|---|
| **A(推奨)** | API が Mailpit の API に、宛先のドメイン `demo-{チームID}.invalid` で問い合わせて返す。画面は API だけを呼ぶ。結果の宛先がすべてそのドメインかを API で確かめてから返す。デモチームを消すとき、Mailpit の該当メールも消す |
| B | API がデモのときだけ、送ったメールの写し(件名・宛先・本文)を自分の DB に残し、それを返す |

推奨の理由:A は notify-relay を通って実際に届いたメールそのものを見せられる(面接官が見たいのは「どんなメールが届くか」)。B は送る前の写しなので、relay や配信の不具合があっても画面では分からない。A で Mailpit に依存するのはデモと作業環境だけで、本番相当の設定(デモ無効)では使わない。

### 判断4. デモユーザーとログインの扱い

| 案 | 内容 |
|---|---|
| **A(推奨)** | デモチームごとに架空のユーザー(代表1・役員1・コーチ2・保護者約20)を作り、ユーザーとチームに「デモ」の印と期限を持つ。ログインは選んだ役割のユーザーとして通常のセッションを作る。役割の切り替えは、セッションに記録した「自分が作ったデモチーム」のユーザーにだけ切り替えられる |
| B | 訪問者用のユーザーを1人だけ作り、役割の切り替えのたびにそのユーザーの役割を書き換える |

推奨の理由:A なら代表と保護者で見える画面の違い(spec のユーザーストーリー)を、既存の権限の仕組みのままで見せられる。B は役割を書き換えるので、「誰が送ったか」「誰が既読か」の表示が崩れる。

### 判断5. デモで止める操作と、止め方

| 案 | 内容 |
|---|---|
| **A(推奨)** | デモモードでは、マジックリンクの発行・使用、チームの作成、メールアドレスの変更、招待からの参加申請を API で 403 にする(デモユーザーかどうかではなく、デモモードかどうかで止める)。画面はデモモードのとき入力欄やボタンを出さず、理由を表示する |
| B | デモユーザーのときだけ止め、デモモードでもマジックリンクは使えるようにする |

推奨の理由:spec の目的は「実在の人が登録して個人情報を入れることを防ぐ」(AC-007-03)。B だとデモ環境に実在の人が登録できてしまう。

### 判断6. 作成の上限とアラート、監視の指標

| 案 | 内容 |
|---|---|
| **A(推奨)** | 作成は IP ごとに1時間20回(AC-007-09)。存在するデモチームが500を超えたら作らず、エラーのログを出す(今のアラートの運用と同じ)。作成数・削除数・存在する数は、作成と削除のたびにログに出す。メトリクスとしての送信は T32(トレース)と一緒に行う |
| B | 指標を今すぐ OpenTelemetry のメトリクスで送る |

推奨の理由:監視の仕組み(Grafana)の整備は、このあとの運用の作業でまとめて行う。今は数を正しく残すことを優先する。

## 作業の順

作業分解は tasks.md。spec は判断1・2に合わせて更新した。デモサーバーでの公開は、このあとサーバーを決めてから行う。
