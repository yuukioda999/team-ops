# 002 招待と参加承認:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断した点は ADR-0010〜0012 に記録した。

## 全体の流れ

```
[Web] 代表・役員がチームの「メンバーを招待」を開く
  → [API] POST /api/teams/{team}/invitation(発行)。古いリンクは無効にする(AC-002-02)
  → 画面に URL と QR コード。LINE などに貼る
[保護者] リンク /join?token=... を開く
  → [API] GET /api/invitations/preview(チーム名だけ返す。無効なら「リンクが無効です」)
  → 未ログインならログイン(001 のマジックリンク)→ 参加申請画面に戻る(判断1)
  → [API] POST /api/invitations/applications(表示名・ひとこと)→ 承認待ち
  → 代表・役員にメール(アウトボックス → notify-relay)
[代表・役員] 承認待ちの一覧 → 役割(保護者/コーチ)を選んで承認、または却下
  → 承認:メンバーになり、本人にメール。却下:通知なし、本人の画面に「承認されませんでした」
```

## 判断した点(2026-11-07 小田がすべて推奨案で決定)

### 判断1. 未ログインで招待リンクを開いた人を、ログイン後に申請画面へ戻す方法(AC-002-05)

今の戻り先は、同じタブの中にしか残らない(001 最終レビューの J)。ログイン用のメールのリンクは新しいタブで開くことが多いので、そのままだと保護者はログインしたあと、もう一度 LINE のリンクを開き直す必要がある。保護者が一番多く通る道なので、ここは手間を減らしたい。

| 案 | 内容 |
|---|---|
| **A(推奨)** | ログイン用リンクを要求するときに戻り先(`/join?token=...` など、決まった形のパスだけ)を API に渡し、ログイン用メールのリンクに含める。確認画面でログインしたら、その戻り先に進む。メール変更の確認(D5)も同じ仕組みで戻れるようになる |
| B | 今のまま。ログイン画面に「ログインしたら、もう一度招待リンクを開いてください」と案内する |
| C | 戻り先をブラウザの localStorage に保存する(同じブラウザの別タブでも読める)。メールアプリの中のブラウザで開いた場合は戻れない |

推奨の理由:メールのリンクを別のアプリやブラウザで開いても戻れるのはAだけ。戻り先は決まった形のパスに限り、外部のURLは受け付けない(001 の safeNext と同じ考え方)。001 の API と画面にも手が入るので、001 の spec に受け入れ基準を1つ足す。

### 判断2. 招待リンクのトークンの持ち方(AC-002-01)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 照合用の SHA-256 と、暗号化したトークンの両方を持つ。代表・役員はあとから同じリンクと QR を何度でも表示できる |
| B | ログイン用と同じく SHA-256 だけを持つ。リンクは発行した直後にしか表示できず、もう一度表示するには発行し直す(古いリンクは無効になる) |

推奨の理由:招待リンクは7日間、LINE に貼ったまま使い続けるもの。Bだと「さっきのQRをもう一度見せたい」ときに発行し直すしかなく、すでに LINE に貼ったリンクが無効になる。暗号化の鍵は APP_KEY(ADR-0003 と同じ扱い)。

### 判断3. 複数の役割の持ち方(AC-002-12、004)

今の team_memberships は役割を1つしか持てない。002 で「保護者とコーチの両方」を選べるようにする必要がある(004 の「複数可」とも同じ)。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 役割を別の表(team_member_roles:メンバーシップごとに役割1行)に分ける。新しいマイグレーションで今の role 列の値を移し、列を削除する |
| B | team_memberships に roles(JSON)列を持つ |

推奨の理由:Aなら「代表は各チームに1人だけ」「役割が1つもない状態は作れない」(004)を DB の一意制約と問い合わせで扱いやすい。JSON は検索と制約が弱い。既存のマイグレーションは書き換えず、新しいマイグレーションを足す。

### 判断4. 権限の判定(TeamPolicy)を作る時期(AC-002-04、AC-002-14)

001 最終レビューで「004 の最初に TeamPolicy を作る(T34)」と決めた。しかし 002 で、すでに「コーチ・保護者は 403」の判定が要る。

| 案 | 内容 |
|---|---|
| **A(推奨)** | T34 を 002 に前倒しする。TeamPolicy に 002 の操作(招待リンクの発行・無効化、承認・却下)を足し、004 の権限表に沿って判定する。役員の役割の値は今決めておく(任命は 004) |
| B | 002 では Controller で代表・役員かを確かめ、004 で Policy に移す |

推奨の理由:B は CLAUDE.md の「判定は Policy に集約する」に反し、004 で書き直しが出る。A なら 004 の網羅テスト(AC-004-01)の土台が 002 でできる。

### 判断5. 参加申請の「表示名」の扱い(AC-002-06)

001 で、表示名はアカウントに1つ持っている。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 申請画面の表示名は、アカウントの表示名を最初から入れて表示する。変えたら、アカウントの表示名も変わる(全チーム共通)。初めてログインした人は、001 の表示名の入力画面を飛ばし、申請画面でまとめて入力する |
| B | チームごとに表示名を持つ(メンバーシップに表示名を持つ) |

推奨の理由:001 の作りと合い、保護者の入力が1回で済む。チームごとに名前を分けたい要望は、まだない。

### 判断6. 「ひとこと」に入る個人情報の扱い(AC-002-06、ADR-0003)

「○年 △△の母です」のように、子どもの名前や学年が入る。

| 案 | 内容 |
|---|---|
| **A(推奨)** | ひとことは暗号化して保存する。承認・却下・自動取り消しで最終状態になったら、ひとことを消す。最終状態の申請の行は30日後に消す(「承認されませんでした」の表示に使う間だけ残す) |
| B | 暗号化して保存し、申請の行と一緒にずっと残す |

推奨の理由:ADR-0003 の「持つ情報は期限付きで扱う」に合う。承認後は名簿(003)で扱う情報なので、申請に残す理由がない。

### 判断7. 却下された人の再申請(spec に記載なし)

AC-002-09 は「承認待ちの間に同じ人がもう一度申請」だけを決めている。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 却下・自動取り消しのあとは、同じリンクから再申請できる。リンク漏えいの対策は AC-002-10(24時間に50件)に任せる |
| B | 却下された人は、同じリンクからは再申請できない(新しいリンクなら申請できる) |

推奨の理由:役員の押し間違いや、ひとことの書き忘れで却下された保護者が困らない。嫌がらせの申請は、却下すれば済み、件数の上限もある。spec に AC-002-16 として足す。

### 判断8. 監査ログの仕組みを作る時期(spec の補足)

spec の補足に「招待リンクの発行・無効化・承認・却下は監査ログに残す」とあるが、監査ログの仕組みはまだない。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 002 で最小限の監査ログを作る。表 audit_logs(チーム、操作した人、操作の種類、対象、時刻、個人情報を含まない補足)と、記録する部品(Support/Audit)。閲覧画面は 004(権限表の「監査ログの閲覧」) |
| B | 監査ログは 003(名簿)でまとめて作り、002 の操作はあとから記録する |

推奨の理由:B だと 002 の操作が記録されない期間ができる。最小限なら作る量は小さく、003・004 でそのまま使える。

### 判断9. QR コードの作り方(AC-002-01)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 画面(ブラウザ)で、表示中の URL から QR コードを作る。npm の `qrcode` を追加する |
| B | API で SVG を作って返す(PHP のライブラリを追加する) |

推奨の理由:QR は URL を絵にするだけで、サーバーで作る理由がない。トークンを含む画像を API の応答やログに増やさずに済む。

## そのほかの方針(既存のADR・spec に沿うもの)

| 項目 | 内容 | 根拠 |
|---|---|---|
| トークン | 32バイトの乱数(256ビット) | AC-002-01(128ビット以上) |
| 有効期限 | 発行から7日。チームで有効なリンクは1つ(発行すると古いリンクの無効化と同じトランザクション) | AC-002-01・02 |
| リンクの形 | Web の `/join?token=...`。画面が読んだらすぐ URL から消し、nginx のログに残さない | 001 の D7 と同じ |
| 無効なリンク | 期限切れ・無効化・存在しないを区別せず、同じ応答と同じ文言 | AC-002-07、推測させない |
| 申請の上限 | リンクごとに直近24時間の申請を数え、51件目から 429。代表へのメールは、リンクごと・1日1通まで(重複防止キーで止める) | AC-002-10 |
| 承認待ちの人 | メンバーではないので、チームのデータは今と同じく404 | spec の補足、AC-000-01 |
| 役割の選択 | 承認で選べるのは保護者・コーチだけ(両方可)。役員・代表を送ったら 422 | AC-002-12・14 |
| 自動取り消し | 申請から14日で取り消す処理を、毎日の定期実行に入れる | AC-002-15 |
| 通知メール | 申請の通知(代表・役員全員へ1通)と承認の通知(本人)。却下は送らない。どれもアウトボックス経由 | AC-002-06・12・13、ADR-0002 |
| 申請者の画面 | 「チームを用意しましょう」の画面に、承認待ち・承認されなかった申請を表示する | AC-002-09・13 |

## データ(team-ops スキーマ)

| 表 | 主な列 |
|---|---|
| team_invitations | id, team_id, token_hash(一意), token(暗号化、判断2), created_by, expires_at, revoked_at, timestamps |
| team_join_requests | id, team_id, invitation_id, user_id, message(暗号化、NULL可、判断6), status(pending / approved / rejected / cancelled), decided_by, decided_at, timestamps。承認待ちは (team_id, user_id) で1件まで |
| team_member_roles | id, membership_id, role(representative / officer / coach / parent)。(membership_id, role) で一意。代表は (team_id, role=representative) で1件まで(判断3) |
| audit_logs | id, team_id, actor_user_id, action, subject_type, subject_id, details(JSON、個人情報なし), created_at(判断8) |

## テスト

- API:受け入れ基準ごとの Feature テスト。403 の判定は TeamPolicy の役割ごとのテスト(判断4)
- テナント分離:承認待ちの人と他チームのメンバーが、チームのデータと承認待ちの一覧を見られないこと(tests/Tenancy)
- ログ:ひとこと・表示名・トークンがログに出ないこと(AC-000-04 と同じ検査)
- Web:画面ごとに Testing Library
- E2E:代表がリンクを発行 → 別の人がリンクからログイン・申請 → 代表が承認 → 申請者がチームを見られる

## 関連するADR

- ADR-0010 招待リンクの持ち方と、ログイン後に元の画面へ戻す方法(判断1・2・9)。戻り先はログイン用のトークンと一緒に保存し、メールの URL には含めない形にした(下の「実装の詳細」)
- ADR-0011 役割は別の表に持ち、権限の判定は TeamPolicy にまとめる(判断3・4)
- ADR-0012 監査ログは 002 で最小限の仕組みを作る(判断8)

## 実装の詳細(判断を ADR にするときに決めたこと)

- 判断1の戻り先は、ログイン用メールの URL に入れず、ログイン用のトークンの行に保存する。ログインした応答で返し、画面がそこへ進む。どのアプリでメールを開いても戻れるという判断1の目的は変わらない。メールの URL が短くなり、招待リンクのトークンがメールの URL に入らない
- 判断6・7は spec に AC-002-17・16 として足した。判断1は 001 の spec に AC-001-19 として足した
