# 005 お知らせ:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断した点は ADR-0017・0018 に記録した。005 の前に行う T33(notify-relay の7日後の削除)も、ここで扱う。

## 全体の流れ

```
[代表・役員・コーチ] 新しいお知らせ → タイトル・本文・宛先(全員/学年/役割)を入力
                   → 届く人数を確認(0人なら送れない)
                   → 今すぐ送信:公開し、宛先を保存し、1,000人ずつアウトボックスに入れる
                   → 予約:指定日時まで公開しない。日時になったら公開して同じ処理をする
[メンバー全員]       お知らせ一覧 → 自分が宛先のお知らせだけを見る(本文は文字として表示し、URL はリンクにする)
アウトボックス → notify-relay → メール(送信元は共通アドレス)
```

## いまあるもの

- アウトボックス(ADR-0002):payload は暗号化。毎分の outbox:redispatch で、notify-relay が止まっていても復旧後に送り直す(AC-005-07 はこの仕組みで満たす)
- スケジューラ(compose の api-scheduler で schedule:work)
- TeamPolicy と権限表の網羅テスト(ADR-0016)。005 の2行は PENDING にあり、この機能で移す
- 監査ログ(ADR-0012)

## 宛先の決め方(spec の表のとおり)

- 全員:チームの全メンバー
- 学年:その学年の選手に紐づく保護者 + 代表・役員・コーチ全員
- 役割:選んだ役割を持つメンバー
- どれでも送信者本人を足し、同じ人は1回だけにする。宛先は送信時点の名簿で決める(AC-005-12)

## 判断した点(2026-11-07 小田がすべて推奨案で決定)

### 判断1. タイトルと本文を暗号化して保存するか

お知らせの本文には、子どもの名前や集合場所など、個人に関わることが書かれうる。

| 案 | 内容 |
|---|---|
| **A(推奨)** | タイトルと本文を暗号化して保存する(表示名と同じ、ADR-0003) |
| B | 平文で保存する(本文の検索ができる) |

推奨の理由:ADR-0003 は個人情報を暗号化して持つとしている。お知らせの検索は受け入れ基準になく、一覧は新しい順に並べるだけなので、暗号化しても困らない。

### 判断2. 送信時点の宛先の保存の仕方(006 の母数)

| 案 | 内容 |
|---|---|
| **A(推奨)** | お知らせごとの宛先の表に、ユーザーIDで保存する。あとで除名されても行は残す(006 の母数が変わらない)。除名された人はチームに入れないので、お知らせも見られない |
| B | メンバーシップIDで保存し、除名で一緒に消す |

推奨の理由:006 の「何人中何人が読んだか」の母数は、送った時点の人数であるべき。B だと除名のたびに母数が減る。宛先の表にはメールアドレスを持たない(送るときにユーザーから読み、アウトボックスの中だけに暗号化して持つ)。

### 判断3. 予約中のお知らせを見られる人(AC-005-10)

spec は「作成者または代表・役員が編集・取り消しする」としているが、予約中のお知らせの一覧を誰が見られるかは書いていない。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 予約中のお知らせは、作成者と代表・役員だけが見られる(編集・取り消しできる人と同じ)。公開前は宛先の人にも見せない |
| B | 作成者だけが見られる |

推奨の理由:編集・取り消しできる人が、一覧で見つけられる必要がある。宛先の人に公開前に見せると、AC-005-09(指定日時まで公開しない)に反する。

### 判断4. 予約の公開の仕組み(AC-005-11)

| 案 | 内容 |
|---|---|
| **A(推奨)** | スケジューラで毎分、予約日時を過ぎたお知らせを公開する(1件ずつ行をロックして、二重に公開しない)。公開と宛先の保存とアウトボックスへの登録を1つのトランザクションで行う |
| B | 予約のときに、指定日時に実行されるキューのジョブを入れる |

推奨の理由:A は今あるスケジューラ(outbox:redispatch と同じ)で済み、編集や取り消しでジョブを消す必要がない。スケジューラが止まっていても、再開した次の分にまとめて公開される。B は予約の変更・取り消しのたびにジョブを差し替える必要があり、キューが失われると公開されない。

### 判断5. お知らせの監査ログ

spec に記録の基準はない。ADR-0012 はチームの重要な操作を記録するとしている。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 送信・予約・予約の編集・取り消し・予約の公開を記録する(ID と宛先の種類、人数だけ。タイトルや本文は残さない)。閲覧は記録しない |
| B | 記録しない |

推奨の理由:誰がいつ何人に送ったかは、トラブルのときに確かめたくなる。閲覧は名簿と違い、宛先の本人が自分宛ての連絡を読むだけなので記録しない(006 の既読で別に扱う)。

### 判断6. 本文の URL をリンクにする範囲(AC-005-16)

| 案 | 内容 |
|---|---|
| **A(推奨)** | `http://` と `https://` で始まる URL だけをリンクにする。新しいタブで開き、`rel="noopener noreferrer nofollow"` を付ける。それ以外(`javascript:` など)は文字のまま |
| B | `www.` で始まるものや、メールアドレスもリンクにする |

推奨の理由:A は XSS の入口になりうる書き方をリンクにしない。HTML として解釈せず、React の文字の表示に任せ、リンクの部分だけを `<a>` にする。

### 判断7. T33:notify-relay の7日後の削除の作り方(AC-R001-22)

| 案 | 内容 |
|---|---|
| **A(推奨)** | relay の中で1時間ごとに、受付から7日を過ぎた依頼を1,000件ずつ消す(宛先と重複防止キーも一緒に消える)。まだ最終状態になっていない宛先が残っていても消す。消した件数をログに出す |
| B | 1日1回、決まった時刻に消す |

推奨の理由:再送は最大でも約2時間で終わるので、7日たって最終状態でない依頼は、止まったまま残ったものと考えられる。1時間ごとにすると、relay が止まっていた日があっても、動いている間にこまめに消せる。1,000件ずつにして、DB を長くロックしない。

## データ(team-ops スキーマ)

- notices:id、team_id、author_user_id、title(暗号化)、body(暗号化)、target_type(all / grades / roles)、target_values(学年または役割の一覧)、status(scheduled / published / cancelled)、scheduled_at、published_at、recipient_count
- notice_recipients:notice_id、user_id(一意)。006 で既読・配信状況の列を足す
- アウトボックスの重複防止キー:`team:{チームID}:notice:{お知らせID}:part:{分割番号}`(spec の補足に、アウトボックスの規約のチームIDを付けた)。宛先はユーザーIDの順に並べて1,000人ずつに分ける

## API

| メソッドとパス | 内容 | 権限 |
|---|---|---|
| GET /api/teams/{team}/notices | 自分が宛先の公開済みのお知らせ(新しい順) | メンバー全員 |
| GET /api/teams/{team}/notices/{notice} | 1件。宛先でなければ404 | メンバー全員 |
| POST /api/teams/{team}/notices/recipient-count | 宛先の指定から、届く人数を返す | 代表・役員・コーチ |
| POST /api/teams/{team}/notices | 今すぐ送信、または予約 | 代表・役員・コーチ |
| GET /api/teams/{team}/notices/scheduled | 予約中のお知らせ | 作成者のもの、代表・役員は全部 |
| PATCH /api/teams/{team}/notices/{notice} | 予約中のものだけ編集。送信済みは 409 で、新しいお知らせで訂正するよう案内(AC-005-06) | 作成者、代表・役員 |
| DELETE /api/teams/{team}/notices/{notice} | 予約の取り消し | 作成者、代表・役員 |

予約日時は ISO 8601(時差付き)で受け取り、5分後〜30日後をサーバーで確かめる(AC-005-13)。画面は日本時間で入力する。

## 画面

- /teams/:teamId/notices:お知らせ一覧(自分宛て)。作成できる人には「お知らせを書く」と、予約中の一覧への導線
- /teams/:teamId/notices/new:作成(宛先の選択、届く人数、今すぐ送信/予約)
- /teams/:teamId/notices/:noticeId:お知らせの表示(本文は文字として表示し、URL はリンク)
- /teams/:teamId/notices/scheduled:予約中の一覧と、編集・取り消し
- チームのホームに、お知らせの最新数件と一覧への導線

## テスト

- 受け入れ基準ごとの Feature テスト、テナント分離、契約テスト、画面のテスト
- 権限表の 005 の2行を PENDING から移す。AC-004-02(コーチ兼保護者がお知らせを作成できる)もここで確かめる
- 1,001人以上の宛先で、分割と重複がないこと(AC-005-08)
- notify-relay を止めた状態で送り、復旧後に1通ずつ届くこと(AC-005-07)を、Feature テスト(送信の失敗を作る)と E2E の障害訓練で確かめる
- relay:削除処理のテーブル駆動テスト(7日を過ぎたものだけ消える、1,000件ずつ)
