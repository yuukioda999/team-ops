# 008 負荷試験:実装計画

spec.md の受け入れ基準をどう作るかを決める。

## 全体の流れ

```
[GitHub Actions を手で実行(規模と試験の種類を選ぶ)]
  → compose で API・worker・scheduler・notify-relay・MySQL・受け取り役を起動
  → 試験用のデータを作る(1万チーム × 30人、各チームに同じ時刻の予約のお知らせ)
  → 試験
      relay 単体:k6 → notify-relay → 受け取り役
      全体:予約の時刻 → scheduler が公開 → アウトボックス → worker → notify-relay → 受け取り役
      配信の最中の API:全体の試験と同時に、k6 → web と同じ道筋で API
  → 結果(k6・受け取り役の数え・DB の時刻・CPU とメモリ)を loadtest/results/ に残す
```

## いまの作りで、詰まりそうな所(測る前の見立て)

測って確かめる前の見立てで、結論ではない。

| 段階 | いまの作り | 見立て |
|---|---|---|
| 予約の公開 | scheduler が毎分、時刻の来た予約を1件ずつ、トランザクションの中で公開する(宛先の決定・保存、アウトボックスへの書き込み) | 1万件を1つの処理で順に公開するので、ここが最初に詰まる可能性が高い |
| アウトボックス → relay | worker は1つ。1件ずつ relay に HTTP で依頼する | 1万件の依頼を1つの worker で順に送る |
| relay の送信 | 同時に50通まで(`SEND_CONCURRENCY`) | 受け取り役の待ち時間しだい |
| DB | API と relay が同じ MySQL(スキーマは別) | 書き込みが集中する |

## 判断1. 進め方(2026-11-09 に AI が示し、2026-11-13 に小田が「推奨で」と決定)

- spec 008 として、受け入れ基準から進める
- GitHub Actions で手で実行し、結果をリポジトリに残す
- 受け取り役は、受け取ったメールを捨てるだけの SMTP サーバーを Go で作る(Mailpit は30万通を溜めると先に詰まる)
- 試験は3つ(relay 単体、全体、配信の最中の API)

## 判断2〜6(2026-11-13 小田が「推奨で」と決定。ADR-0023)

## 判断2. 試験用のデータをどう作るか(AC-008-02・03)

宛先のメールアドレスと表示名は暗号化して保存し、メールアドレスにはブラインドインデックスを付けている(ADR-0003)。そのため、作るには Laravel の鍵と処理が要る。

| 案 | 内容 |
|---|---|
| **A(推奨)** | API に試験用の artisan コマンド(`loadtest:seed`)を作る。暗号化は Laravel の処理を使い、行はまとめて insert して速くする。`APP_ENV` が `local`・`testing`・`loadtest` 以外では止まる |
| B | 公開している API を k6 で叩いて作る。本物の流れを通るが、1万チームの登録と招待の承認に数時間かかる |
| C | SQL で直接作る。暗号化できないので使えない |

## 判断3. 配信の最中の API の試験で、どうログインするか(AC-008-07)

| 案 | 内容 |
|---|---|
| **A(推奨)** | `loadtest:seed` が、試験用の利用者(各チームの代表と保護者の一部)のセッションを作り、Cookie を k6 に渡す。ログインの流れは001 の E2E で確かめているので、この試験では測らない |
| B | k6 が実際にマジックリンクでログインする。受け取り役からリンクを読み出す仕組みが要り、ログイン用リンクの回数制限にも当たる |

## 判断4. 受け取り役の待ち時間(AC-008-01)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 1通あたり 50ms を標準にする(メール送信サービスの応答を模す)。比較のため 0ms でも1回測る |
| B | 0ms だけ。relay の上限は分かるが、本物の SMTP より楽な条件になる |

## 判断5. CPU とメモリの制限

| 案 | 内容 |
|---|---|
| **A(推奨)** | 目標は制限なし(GitHub Actions のマシン全体、4コア・16GB)で測る。参考に、デモの VPS と同じ制限(3コア・2GB)をかけた全体の試験も1回測って記録する |
| B | 制限なしだけ |
| C | VPS と同じ制限だけ。目標の規模(1万チーム)は1台の 2GB の VPS を想定していないので、目標に届かないのは当然になる |

## 判断6. 受け取り役と k6 の置き場所

| 案 | 内容 |
|---|---|
| **A(推奨)** | team-ops の `loadtest/` に置く(k6 のシナリオ、受け取り役の Go、結果)。受け取り役は標準ライブラリだけで作り、外部のライブラリを足さない。要件の「成果物と置き場所」(loadtest/)のとおり |
| B | 受け取り役を notify-relay のリポジトリに置く。relay の試験の道具としては近いが、relay は業務アプリから独立した OSS で、試験の構成は team-ops の領分 |

## 直し方(AC-008-10)

直す前の測定(1万チーム、2026-11-13)で、詰まっている所は次の3つと分かった(loadtest/README.md)。

1. アウトボックスから relay への依頼(worker が1つで、1件ずつ依頼する)
2. 予約の公開(scheduler が順に公開する)
3. relay の送信(500件ずつ取り出し、全部が終わるまで次を取り出さない。1通ごとに接続する)

AI が「段階1:設定だけを変えて測る → 段階2:足りない所だけコードを直す」を推奨し、2026-11-13 に小田が「推奨で進めて」と決定した。

- **段階1**:worker を 1 → 4、`SEND_CONCURRENCY` を 50 → 150。一度に取り出す数(500)は relay の設定では変えられないので、段階1には入れない

## PR での確認(レビューの指摘11、2026-11-13)

道具を変えた PR では、1,000チームの規模で relay 単体と全体を自動で動かし、道具が壊れていないかを確かめる。同じ名前の API・relay のブランチがあれば、それを使う。PR の数字は結果としては扱わず、結果は手で実行した回だけを `loadtest/results/` に残す。

## 結果の残し方

- `loadtest/results/YYYY-MM-DD-<試験>-<規模>/`:k6 の要約(JSON)、受け取り役の数え、段階ごとの時刻(DB から取り出す)、`docker stats` の記録
- `loadtest/README.md`:目標、条件、直す前と後の表、詰まっていた所と直し方、次の手
- 数字は GitHub Actions のマシンでの値で、本番のサーバーの性能を表すものではないことを明記する
