# 008 負荷試験

## 概要

要件の非機能の目標(project-brief.md)を、実際に負荷をかけて確かめる。今の作りで測り、詰まっている所を見つけて直し、直す前と後の数字を記録して公開する。

目標:

- 朝6時台に **30万通(1万チーム × 30人)を10分以内**に送り終える(毎秒500通)
- 主要な API の **p95 が 300ms 以下**
- 配信の最中でも、画面の速さが落ちない(ADR-0004 で「負荷試験で確かめる」とした点)

この spec は機能ではなく、試験の道具と、試験の結果を受け入れ基準にする。目標を満たせなかったときも、測った数字と原因と次の手を記録すれば、受け入れ基準は満たす(数字をよく見せるために条件を変えない)。

## ユーザーストーリー

- 面接官として、「30万通を10分」が、主張だけでなく測った数字で示されているのを見たい
- 開発者として、どこが詰まっているかを数字で見つけ、直した効果を確かめたい
- 開発者として、同じ条件で何度でも測り直せるようにしたい

## 試験の条件(すべての試験で共通)

- 実行する場所:GitHub Actions のマシン(ubuntu-latest)。毎回同じ性能のマシンで測る
- 起動する構成:開発用の compose と同じサービス(API・worker・scheduler・notify-relay・MySQL)。API と relay は本番と同じイメージ
- メールの送り先:受け取ったメールを捨てるだけの SMTP サーバー(以下、受け取り役)。本物の SMTP の遅れを模すため、1通ごとに決まった時間だけ待ってから応答できる
- データ:試験用のチームと宛先を、試験の前にまとめて作る。宛先はすべて `.invalid` で、外には出ない
- 結果:k6 の結果、受け取り役の数え、サービスごとの CPU・メモリを、`loadtest/results/` に日付ごとに残す

## 受け入れ基準

### 道具

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-008-01 | なし | 受け取り役に SMTP でメールを送る | 受け取って捨て、受け取った数・最初と最後の時刻を HTTP で返す。指定した待ち時間だけ遅れて応答する |
| AC-008-02 | なし | 試験用のデータを作るコマンドを実行する | 指定した数のチーム(1チーム30人)と、各チームに同じ日時の予約のお知らせを1件ずつ作る。1万チームを10分以内に作れる |
| AC-008-03 | `APP_ENV` が `local`・`testing`・`loadtest` 以外 | 試験用のデータを作るコマンドを実行する | 何も作らずに止まる(本番のデータに混ざらない) |
| AC-008-04 | なし | GitHub Actions で試験を手で実行する | 規模(チーム数)と試験の種類を選んで実行でき、結果がファイルとして残る |

### 試験と結果

| ID | 試験 | 測ること | 目標 |
|---|---|---|---|
| AC-008-05 | relay 単体:1,000宛先の配信依頼を300件、k6 から直接 notify-relay に送る | 最初の依頼を受け付けてから、受け取り役が30万通を受け取るまでの時間。受付 API の p95 | 10分以内。受付の p95 300ms 以下 |
| AC-008-06 | 全体:1万チームの予約のお知らせを同じ時刻に公開させる | 予約の時刻から、受け取り役が30万通を受け取るまでの時間。途中の段階(公開、アウトボックス、relay への依頼、送信)ごとの時間 | 10分以内 |
| AC-008-07 | 配信の最中の API:AC-008-06 の最中に、k6 で利用者の主な操作(ホーム、お知らせ一覧、お知らせの表示、配信状況、名簿)を続ける | 操作ごとの p95 と失敗の割合。配信がないときとの差 | p95 300ms 以下。失敗 1% 未満 |
| AC-008-08 | AC-008-05・06 | 同じメールが2通届いていないか | 受け取り役が受け取った数がちょうど30万通(二重配信と取りこぼしがない) |

### 改善と記録

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-008-09 | 最初の測定(直す前) | 結果をまとめる | 目標との差と、詰まっている所(どのサービスの何が時間を使っているか)を、数字を根拠に `loadtest/README.md` に書く |
| AC-008-10 | 詰まっている所が分かった | 直す | 直し方ごとに、選択肢と推奨を示して人間が決める。設計を変える場合は ADR を書く |
| AC-008-11 | 直したあと | 同じ条件で測り直す | 直す前と後の数字を並べて `loadtest/README.md` に残す。目標を満たせなかった場合は、その数字と原因と次の手を書く |
| AC-008-12 | なし | 結果を公開する | team-ops の README から、結果へたどれる |

## 範囲外

- 本物の SMTP の送信サービスに対する試験(送信の上限は、サービスの契約で決まるため)
- デモの VPS(2GB)での試験。目標の規模はデモ環境のものではない。参考に、本番と同じ CPU・メモリの制限をかけた測定は、計画の判断で扱う
- 秒あたりの流量制御(notify-relay の「これから」)。必要と分かった場合は、別の spec にする
