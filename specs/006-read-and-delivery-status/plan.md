# 006 既読・配信状況・再通知:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断した点は ADR-0019・0020 に記録した。

## 全体の流れ

```
[メンバー]           お知らせを開く → 既読(初めて開いた日時)
                    一覧で未読に目印。自分宛てのメールが恒久的に失敗していたら、アドレスの確認を促す
[代表・役員・作成者]  状況を開く → 宛先数・既読・未読・送信失敗(送信中なら送信済み・送信待ち)
                    未読者の一覧、送信失敗の一覧(理由は利用者向けの言葉)
                    「未読の人に再通知」→ 実行時点の未読者に【再通知】のメール(1時間に1回、1つのお知らせに3回まで)
notify-relay → (webhook)結果 → Laravel が宛先ごとの状態を更新(event_id で重複を除く)
定期処理(1時間ごと)→ 結果が届いていない依頼を notify-relay に照会し、件数を照合。食い違いはログとアラート
```

## いまあるもの

- 送信時点の宛先(notice_recipients、ユーザーID)。006 の母数(ADR-0017)
- アウトボックス:宛先の recipient_ref は `user_{ユーザーID}`、重複防止キーは `team:{チーム}:notice:{お知らせ}:part:{番号}`(ADR-0018)
- ログイン後に元の画面へ戻る仕組み(AC-001-19)。AC-006-02 はこれで満たせるかを確かめ、足りなければ直す
- 権限表の網羅テスト。006 の行は PENDING にあり、この機能で移す

## いまないもの(006 の前提)

notify-relay の結果の通知と照会は、001 の受け入れ基準にあるがまだ作っていない。006 はこれがないと作れない。

- AC-R001-16〜20:結果の webhook(500件または5秒でまとめる、完了通知、署名、24時間の再送、401 は再送しない)
- AC-R001-21:依頼の状態の照会(件数だけ)
- Laravel 側:webhook の受け口、notify-relay が返した delivery_id の保存(照会に使う)

## 判断した点(2026-11-07 小田がすべて推奨案で決定)

### 判断1. notify-relay の webhook と照会を、どこで作るか

| 案 | 内容 |
|---|---|
| **A(推奨)** | 006 の作業として、relay の AC-R001-16〜21 を先に作る(relay の別のプルリクエスト)。そのあと Laravel・画面を作る |
| B | webhook は作らず、Laravel が定期的に照会する(AC-R001-21 だけ作る) |

推奨の理由:spec の補足と ADR-0002 は webhook で結果を返す前提。照会は件数だけで宛先ごとの状態が分からないので、B では未読・失敗の一覧(AC-006-05・06)を作れない。

### 判断2. 宛先ごとの配信状態の持ち方

| 案 | 内容 |
|---|---|
| **A(推奨)** | notice_recipients に列を足す:既読日時、配信状態(送信待ち・送信済み・失敗・送らなかった)、失敗の理由、結果の発生日時。webhook の event_id は別の表で重複を除く |
| B | 配信の結果を別の表(依頼×宛先ごとの行)に持ち、画面のたびに集計する |

推奨の理由:お知らせ×メンバーで1行なので、既読と配信状態を同じ行で数えられる(既読数・未読数・失敗数が1回の集計で出る)。再通知の結果も同じ行を更新し、結果の発生日時が新しいほうを採る(webhook の到着順は保証されないため)。宛先を .invalid に限る環境で送らなかった人は、送信時に「送らなかった」にする。

### 判断3. 「恒久的な失敗」の範囲

| 案 | 内容 |
|---|---|
| **A(推奨)** | relay の error_code が `invalid_address`(アドレスが存在しない・形式不正)のときだけを恒久的な失敗とする。本人への表示(AC-006-16)と再通知の除外(AC-006-14)の両方に使う |
| B | `provider_rejected`(アドレス以外の理由で拒否)も恒久的な失敗に含める |

推奨の理由:本人に「メールアドレスを確認してください」と促せるのは、アドレスが原因のときだけ。`provider_rejected` は本人には直せないので、再通知では送り直す(結果は失敗の一覧に理由付きで出る)。

### 判断4. 恒久的に失敗した人を、以後のお知らせのメールから外すか(AC-006-17「以後の送信対象に戻る」)

| 案 | 内容 |
|---|---|
| **A(推奨)** | ユーザーに「メールが届かなかった日時」を持つ。ある間は、お知らせと再通知のメールを送らない(アプリには届き、状態は「送らなかった」)。メールアドレスを変えたら消して、送信対象に戻す。ログインのメールは対象外(アドレスを変えるのに必要) |
| B | 再通知だけで外す。新しいお知らせは毎回送る |

推奨の理由:AC-006-17 の「以後の送信対象に戻る」は、失敗の間は送信対象から外れていることを前提にしている。存在しないアドレスに送り続けると、共通の送信元アドレスの評判が下がる(005 の S2 と同じ理由)。

### 判断5. 既読の記録の仕方

| 案 | 内容 |
|---|---|
| **A(推奨)** | 宛先の本人がお知らせの詳細(GET)を開いたときに、まだなければ既読日時を入れる。一覧を見ただけでは既読にしない。状況の画面を開いても既読にしない |
| B | 画面から「既読にする」API を別に呼ぶ |

推奨の理由:spec の既読の定義(アプリでそのお知らせを開いたとき)に合う。B は呼び忘れや、開かずに API だけ呼ぶことができ、A より壊れやすい。作成者も宛先なので、自分のお知らせを開けば既読になる。

### 判断6. 再通知の制限と記録

| 案 | 内容 |
|---|---|
| **A(推奨)** | お知らせごとに再通知の表(回数・実行した人・送った人数・除外した人数・実行日時)を持つ。前回から1時間以内、または3回済みなら 409 で、次に実行できる時刻を返す。ロックして二重実行を防ぐ。監査ログに残す。重複防止キーは `team:{チーム}:notice:{お知らせ}:reminder:{回数}:part:{番号}` |
| B | お知らせの行に回数と最後の日時だけを持つ |

推奨の理由:誰がいつ何人に再通知したかは、送信と同じく後で確かめたくなる。表にしておけば監査ログと画面の両方で使える。spec の補足の重複防止キー(お知らせID + reminder + 回数 + 分割番号)に、005 と同じくチームIDを前に付ける。

### 判断7. 照合(AC-006-09)の範囲とアラート

| 案 | 内容 |
|---|---|
| **A(推奨)** | 1時間ごとに、受け付けから1時間を過ぎて完了の通知が来ていない依頼を、relay に照会する(7日を過ぎて 404 なら照会をやめる)。件数が Laravel 側と食い違えば、照合の記録を残し、ログに error で出す(アラートは error のログを監視して出す、という今の運用に合わせる)。宛先ごとの状態は照会では直さない |
| B | 食い違いを見つけたら、relay に宛先ごとの結果を送り直させる仕組みも作る |

推奨の理由:照会は件数だけを返す設計(relay の OpenAPI)。B は relay に新しい API が要り、spec の範囲(照合して記録・アラート)を超える。

### 判断8. 状況を見られる人と、画面の場所

| 案 | 内容 |
|---|---|
| **A(推奨)** | 代表・役員はすべて、コーチは自分が作成したお知らせだけ(004 の権限表 ※2)。保護者は 403(AC-006-10)。TeamPolicy に判定を1つ足し、権限表の 006 の行を移す。画面はお知らせの表示画面に「配信状況」へのリンクを出し、状況・未読者・失敗の一覧・再通知を1つの画面にまとめる |
| B | 状況の一覧画面を別に作り、送ったお知らせを並べる |

推奨の理由:B は spec にない機能(送ったお知らせの横断の一覧)になる。A は既存の画面からたどれる。
