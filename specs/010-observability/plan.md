# 010 監視:トレースとメトリクス:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断1〜7は、2026-11-19 に AI が選択肢と推奨を示し、同じ日に小田が「全て推奨通り」と決定した(すべて A)。

## いまあるもの

| もの | 状況 |
|---|---|
| ローカルの Grafana 一式 | compose に `otel-lgtm`(Grafana・Tempo・Prometheus・Loki と OTLP の受け口)がある。API も notify-relay も、何も送っていない |
| notify-relay の traceparent | 受付で `traceparent` を受け取り、保存して、webhook に付けて返す(AC-R001-25 の一部)。スパンは作っていない |
| デモ環境の監視 | Grafana Cloud の無料枠に、Alloy でコンテナのログとサーバーの CPU・メモリ・ディスクを送る(ADR-0022)。ログの件数でアラート(monitoring.md) |
| メトリクス | なし。デモチームの数などはログに出しているだけ(ADR-0021) |

## 判断1(決定:A). API の計装の方法

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | PHP の拡張(ext-opentelemetry)と、Laravel の自動計装のパッケージを入れる。HTTP のリクエスト、DB のクエリ、キューのジョブ、外への HTTP(notify-relay への依頼)のスパンと、traceparent の受け渡しが自動でできる。足りない所(公開、照合)だけ手で書く | 手で書く量が少なく、漏れにくい。ただし、URL のクエリ(ログイン用リンクのトークン)や DB の文が属性に入るので、送る前に伏せる処理(span processor)が要る。拡張をイメージに入れる |
| B | 拡張を使わず、SDK だけで、ミドルウェア・ジョブ・HTTP クライアントのスパンを手で書く | 入れるものは少ないが、書く量が多く、DB のクエリの時間などが見えない |

## 判断2(決定:A). notify-relay の計装の方法

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | OpenTelemetry の Go SDK(トレースとメトリクス、OTLP の HTTP の送り口)を入れる。外部ライブラリを足すので、notify-relay の ADR に理由を書く | 業界の標準で、team-ops の受け口(otel-lgtm、Alloy、Grafana Cloud)にそのまま送れる。依存は増える(go.mod に十数個) |
| B | メトリクスだけ Prometheus のクライアントで出し、トレースは traceparent をログに書くだけにする | 依存は少ないが、AC-010-02(1本のトレースでたどる)を満たせない |

## 判断3(決定:A). デモ環境での送り方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | API と notify-relay は、同じサーバーの Alloy に OTLP で送る。Alloy が Grafana Cloud へ送る(ログと同じ道) | Grafana Cloud の鍵を持つのは Alloy だけのまま。アプリの設定は、ローカルと送り先が違うだけ |
| B | API と notify-relay から、直接 Grafana Cloud に送る | Alloy の設定は要らないが、鍵が3か所に散る |

## 判断4(決定:A). ダッシュボードとアラートの持ち方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | ダッシュボード(JSON)とアラートのルール(YAML)をリポジトリに置く。ローカルは otel-lgtm に起動時に読み込ませる。Grafana Cloud には、手順書のコマンドで同じファイルを入れる。通知はメールで、宛先は Grafana Cloud の設定にだけ置く(リポジトリに書かない) | 同じファイルなので、ローカルとデモ環境で食い違わない(AC-010-09)。面接でファイルを見せられる |
| B | Grafana の画面で作り、書き出したものを置いておく | 手早いが、どちらが正しいかがずれる |

## 判断5(決定:A). サンプリング(どれだけのトレースを残すか)

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | ローカルとデモ環境は全部残す。負荷試験では既定で止める(設定で入れられる) | デモ環境の量は少なく、Grafana Cloud の無料枠に収まる見込み。負荷試験で止めるのは、計測が結果を揺らさないため(負荷試験の数字と比べられるように) |
| B | どこでも一部(例:1割)だけ残す | 量は減るが、「この1通」を追えないことがある |

## 判断6(決定:A). CI での確かめ方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 全体の試験(smoke)で otel-lgtm も起動し、E2E のあとに、Tempo に API と notify-relay の両方のスパンを含むトレースがあること、Prometheus に主なメトリクスがあることを問い合わせて確かめる。障害訓練では、対応するアラートの状態が「発火」になったことを確かめる(AC-010-11) | 「送っているはず」ではなく、届いたことを確かめる(監視の修正 #31 の学び) |
| B | 単体テストで、スパンとメトリクスを作ることだけを確かめる | 速いが、送り先に届くかは分からない |

## 判断7(決定:A). SLO と監視の設計の置き場所

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 要件の「成果物と置き場所」どおり、`docs/ops/` に SLO(slo.md)と監視・アラートの設計(alerts.md)を置く。戻し方は、これまでどおり `docs/runbook/` に置き、アラートからリンクする | 要件の置き場所と合う。設計(何を測るか、なぜその閾値か)と、手順(どう戻すか)を分けられる |
| B | すべて `docs/runbook/monitoring.md` に足す | ファイルは増えないが、要件の置き場所と違い、1つのファイルが長くなる |

## 判断8(決定:A). API のルートごとのリクエスト数・失敗数・所要時間の作り方

実装を始めてから出た判断。2026-11-19 に AI が選択肢と推奨を示し、同じ日に小田が推奨どおり A に決めた。

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | API のサーバーのスパン(名前は「メソッド + ルートのひな形」)から作る。ローカルは otel-lgtm の Tempo が作る設定になっている。デモ環境は Alloy でスパンから作って送り、名前をそろえる | アプリに足すコードがない。PHP はリクエストごとにプロセスの状態が消えるため、アプリの中でカウンターを持つ方法は使えない |
| B | API が OTLP のメトリクスを delta(前回からの増分)で送る | Prometheus の delta の受け取りは実験的で、ローカルとデモ環境で数え方がずれやすい |
| C | 件数を DB か Redis に貯めて `/metrics` で出す | 書く量が多く、リクエストごとに書き込みが増える |

## 判断9(決定:A). アウトボックスとデモチームの件数の出し方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | scheduler が毎分コマンドを動かし、DB を数えて OTLP で送る | トレースと同じ送り道で、ローカルとデモ環境で同じ |
| B | `/metrics` を Prometheus の形式で出し、Alloy と otel-lgtm に読みに来させる | 読みに行く設定が2か所に増える |

## 設計判断(ADR)

判断1〜7を [ADR-0026 トレースとメトリクスの方法](../../docs/adr/0026-traces-and-metrics.md) に書いた。判断8・9は ADR-0026 の追記に書いた。notify-relay の依存の追加は、notify-relay の ADR にも書く(notify-relay の CLAUDE.md)。

## 個人情報の扱い(どの案でも守ること)

- スパンの属性・イベント・メトリクスのラベルに、表示名・メールアドレス・本文・ログイン用リンク・トークン・セッションを入れない。URL のクエリは送る前に消す
- DB の文は、値を含まない形(プレースホルダーのまま)だけにする
- 宛先は notify-relay の email_ref も入れない(ラベルの数が際限なく増えるため。AC-010-06)
- これらは、送る前の処理で伏せ、単体テストで確かめる。security-reviewer を必ず動かす
