# 010 監視:トレースとメトリクス

## 概要

API と notify-relay が、トレースとメトリクスを OpenTelemetry で出すようにする。ローカルでは compose の Grafana 一式(otel-lgtm)で、デモ環境では Grafana Cloud で、同じダッシュボードを見られるようにする。SLO を決め、それを外れたら気づけるアラートを置く。

要件(docs/requirements/project-brief.md)のうち、次をこの spec で満たす。

- 監視:サービスをまたいだトレースIDで、1通の通知を配信先まで追跡できること
- 監視はローカルにも Grafana 一式(トレース・メトリクス・ログ)を立て、デモ環境と同じダッシュボードで確認できるようにする
- 成果物:SLO、監視・アラート設計
- notify-relay の AC-R001-24(メトリクス)と AC-R001-25(トレース)。どちらも受け入れ基準はあるが、まだ作っていない

障害訓練の振り返り(docs/postmortems/)で「次の手」とした、次のことにも答える。

- SMTP の一時エラーが続いても、警告のログが出ないので気づきにくい
- 何通が二重に届いたかは、運用の手段では分からない
- アラートの仕組みがない

## ユーザーストーリー

- 運用する人として、配信が遅れている・失敗が増えている・API が遅いことに、利用者からの問い合わせより先に気づきたい
- 運用する人として、「このお知らせのメールが届かない」と言われたとき、そのお知らせの配信を、API から notify-relay の送信まで1本のトレースで追いたい
- 面接官として、SLO と、それを外れたことを示すダッシュボードとアラートを見たい

## 受け入れ基準

### トレース

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-010-01 | なし | API にリクエストする | API のリクエストごとにトレースができ、処理の名前(ルート)と結果(状態コード)が分かる。個人情報(表示名・メールアドレス・本文・ログイン用リンク・トークン)は、属性にもイベントにも入らない |
| AC-010-02 | お知らせを公開する | 配信が終わる | お知らせの公開から、アウトボックスの送信、notify-relay の受付、メールの送信、結果の webhook、API での記録までを、1つのトレースIDでたどれる(notify-relay の AC-R001-25) |
| AC-010-03 | 送り直しが起きた | 配信が終わる | 送り直したアウトボックスと、notify-relay の再送が、同じトレースの中で分かる |

### メトリクス

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-010-04 | notify-relay が動いている | メトリクスを見る | 受付数、送信数(結果とエラーの種類別)、未送信の宛先数、送信の所要時間、webhook の失敗数が分かる(notify-relay の AC-R001-24) |
| AC-010-05 | API が動いている | メトリクスを見る | ルートごとのリクエスト数・失敗数・所要時間、送っていないアウトボックスの数と、いちばん古いものの待ち時間、デモチームの数(ADR-0021)が分かる |
| AC-010-06 | なし | メトリクスのラベルを見る | ラベルに、チームID・利用者ID・宛先など、数が際限なく増える値や個人を指す値を使わない |

### ダッシュボードと SLO

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-010-07 | なし | SLO を読む | API の応答時間(p95 300ms 以下)、API の稼働率(月 99.5%)、配信の成功率(99.9%)、配信の完了までの時間について、測り方と目標が書かれている |
| AC-010-08 | ローカルで `make up` | Grafana を開く | SLO と、配信・API の様子が分かるダッシュボードが、最初から入っている |
| AC-010-09 | デモ環境 | Grafana Cloud を開く | ローカルと同じダッシュボード(同じ定義のファイル)を見られる |

### アラート

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-010-10 | SLO を外れそうな状態(送信の失敗が増える、配信が遅れる、API が遅い・失敗する) | なし | アラートが出る。どのアラートも、手順書(runbook)の戻し方の節につながっている |
| AC-010-11 | 障害訓練(spec 009)のうち、アラートの対象の障害を起こす | なし | 訓練の中で、対応するアラートが出ることを確かめる |

### 確かめ方

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-010-12 | CI | 全体の試験(smoke)を動かす | お知らせを1件送り、API と notify-relay の両方のスパンを含むトレースが1本できること、メトリクスが取れることを確かめる |
| AC-010-13 | なし | ログを見る | ログにトレースIDが入り、ログからトレースへたどれる |

## 範囲外

- 画面(team-ops-web)のトレース(ブラウザからの計測)
- 外部の監視サービスからの死活監視の追加(デモ環境の5分ごとの `/api/health` は ADR-0022 のまま)
- 秒あたりの流量制御(第2弾)
- アラートの通知先の多重化(メール以外)
