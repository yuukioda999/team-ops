# 009 障害訓練と振り返り

## 概要

配信の途中で障害を起こし、設計で約束したこと(ADR-0002・0018・0019、notify-relay の AC-R001-10〜20)が実際に守られるかを確かめる。訓練ごとに振り返り(ポストモーテム)を書き、見つかった穴と次の手を記録して公開する。

確かめる約束:

- notify-relay が止まっても、Laravel が配信依頼を保持し、復旧後に送る。二重には届けない(project-brief.md の非機能要件)
- SMTP の一時エラーは再送し、恒久エラーは再送せずに失敗として記録する(AC-R001-10・11)
- 送信の途中でプロセスが落ちても、最終状態でない宛先から再開する(AC-R001-13)
- 配信結果の通知(webhook)が届かなくても、再送と照合で、配信状況が最後には正しくなる(AC-R001-19、ADR-0019)

この spec は機能ではなく、訓練の道具と、訓練の結果を受け入れ基準にする。約束が守られなかったときも、起きたことと原因と次の手を振り返りに記録すれば、受け入れ基準は満たす(結果をよく見せるために条件を変えない)。

## ユーザーストーリー

- 面接官として、「止まっても二重に届かない」が、主張だけでなく、実際に止めて確かめた記録で示されているのを見たい
- 運用する人として、障害が起きたときに、どう気づき、どう戻すかが手順書に書かれていてほしい
- 開発者として、同じ障害を何度でも起こして確かめられるようにしたい

## 訓練の条件(すべての訓練で共通)

- 構成:開発用の compose と同じサービス(API・worker・scheduler・notify-relay・MySQL・Mailpit)。Mailpit の障害注入(Chaos)で SMTP のエラーを起こす
- データ:負荷試験の試験データの作成(`loadtest:seed`)を使い、予約のお知らせを同じ時刻に公開させる。宛先はすべて `.invalid` で、外には出ない
- 数え方:Mailpit が受け取ったメールを宛先ごとに数え、二重に届いた数と届かなかった数を出す。API の配信状況(notice_recipients)と notify-relay の記録も、最後に照らし合わせる

## 受け入れ基準

### 道具

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-009-01 | なし | 訓練を手で実行する | 訓練の種類を選んで実行でき、起こした障害と時刻、メールの数え、配信状況の照らし合わせ、関係するログが結果として残る |
| AC-009-02 | なし | 訓練の結果をまとめる | 宛先ごとに、届いた回数(0・1・2回以上)と、API の配信状況と、notify-relay の状態が並んで分かる |

### 訓練

| ID | 起こす障害 | 確かめること | 期待する結果 |
|---|---|---|---|
| AC-009-03 | SMTP の一時エラー:配信の途中で、一定の時間だけ Mailpit が一部のメールに 451 を返す | 再送と、最後に届いた数 | 障害を止めたあと、全員にちょうど1通ずつ届く。API の配信状況はすべて「届いた」になる |
| AC-009-04 | SMTP の恒久エラー:Mailpit が一部のメールに 550 を返す | 再送しないことと、失敗の記録 | 550 を返した宛先は再送されず、API の配信状況で「届かなかった」と理由が分かる。ほかの宛先にはちょうど1通ずつ届く |
| AC-009-05 | notify-relay の停止:お知らせの公開の前に notify-relay を止め、しばらくしてから起動する | 停止中に依頼を失わないことと、復旧までの時間 | 停止中は API のアウトボックスに依頼が残る。起動したあと、全員にちょうど1通ずつ届く。起動から最後の1通までの時間を記録する |
| AC-009-06 | notify-relay の強制終了:送信の途中で notify-relay を強制終了(SIGKILL)し、起動し直す | 取りこぼしと二重配信の数 | 取りこぼしはない。二重に届いた数を記録する(送信中だったメールは二重に届きうる。その範囲に収まるかを確かめる) |
| AC-009-07 | 配信結果の受け取りの停止:配信の途中で API を止め、しばらくしてから起動する | 配信状況が最後に正しくなるか | メールはちょうど1通ずつ届く。API の起動後、配信結果の再送(または照合)で、API の配信状況が notify-relay の記録と一致する |

### 振り返りと手順書

| ID | 前提 | 操作 | 結果 |
|---|---|---|---|
| AC-009-08 | 訓練を1つ行った | 振り返りを書く | `docs/postmortems/` に、概要・影響・時系列・どう気づいたか・原因・どう戻したか・次の手を書く。個人を責めない書き方にする |
| AC-009-09 | 訓練で、期待と違う結果が出た | 直す | 直し方を選択肢と推奨で示し、人間が決める。設計を変える場合は ADR を書き、受け入れ基準にないふるまいは先に spec を直す |
| AC-009-10 | なし | 手順書を直す | `docs/runbook/troubleshooting.md` に、障害ごとの気づき方と戻し方を書く |
| AC-009-11 | なし | 結果を公開する | team-ops の README から、振り返りへたどれる |

## 範囲外

- MySQL の停止、ディスクやメモリの不足、サーバーごとの停止(デモの VPS の障害)。必要と分かった場合は、別の spec にする
- 監視とアラートの仕組みを作ること。訓練では、いまある手段(ログ・配信状況の画面・コマンド)でどう気づけるかを記録し、足りなければ次の手に書く
- 本物の SMTP の送信サービスでの訓練
