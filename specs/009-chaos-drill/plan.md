# 009 障害訓練と振り返り:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断1〜6は、2026-11-16 に AI が選択肢と推奨を示し、同じ日に小田が「推奨でいいです」と決定した(すべて A)。

## 全体の流れ

```
[GitHub Actions を手で実行(訓練の種類を選ぶ)]
  → 開発用の compose で API・worker・scheduler・notify-relay・MySQL・Mailpit を起動
  → 試験データを作る(loadtest:seed。チームごとに同じ時刻の予約のお知らせ)
  → 予約の時刻の前後に障害を起こす(Mailpit の Chaos、docker compose stop / kill / start)
  → 全員に届くか、決めた時間まで待つ
  → 数える:Mailpit の宛先ごとの受信数、API の配信状況、notify-relay の宛先の状態、アウトボックス
  → 時系列(障害を起こした時刻・戻した時刻・最初と最後の1通)と、関係するログをジョブのログに出す
  → 人間が確かめてから、docs/postmortems/ に振り返りを書く
```

## いまの作りで、起きるはずのこと(訓練の前の見立て)

訓練で確かめる前の見立てで、結論ではない。

| 訓練 | いまの作り | 起きるはずのこと |
|---|---|---|
| SMTP の一時エラー(AC-009-03) | relay は 4xx を 30秒・2分・10分・30分・1時間の間隔で最大5回再送(AC-R001-10) | 障害を止めれば、遅くとも最後の再送の間隔のあとに届く |
| SMTP の恒久エラー(AC-009-04) | relay は 5xx を再送せず failed(AC-R001-11)。結果は webhook で API へ(ADR-0019) | 配信状況に「届かなかった」と理由が出る |
| relay の停止(AC-009-05) | API のアウトボックスは、30秒・1分・2分・5分・10分・30分の間隔で送り直す | 停止中は依頼が残り、relay の起動後、次の送り直しの時刻に送られる。長く止めるほど、起動から再開までが延びる(最大30分) |
| relay の強制終了(AC-009-06) | 送る直前に `sending` と記録し、起動時に `sending` の宛先を `pending` に戻す(relay の ADR-0002) | 強制終了の時に送信中だった宛先にだけ、二重に届きうる。その数は同時に送る数(`SEND_CONCURRENCY`)以下 |
| 配信結果の受け取りの停止(AC-009-07) | relay は webhook を最大24時間再送(AC-R001-19)。API は1時間ごとに照合(AC-006-09) | API の起動後、webhook の再送で配信状況がそろう |

## 判断1(決定:A). 訓練を動かす場所

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | GitHub Actions の手で実行するワークフロー(`chaos.yml`)。負荷試験と同じく、ジョブのログから結果を写す。手元では同じ手順を `make` で動かせる | 誰でも同じ手順で何度でも動かせ、記録(ジョブのログ)が公開される。負荷試験の道具(試験データ、数え方)を使い回せる |
| B | 手元で `make chaos-*` を人間が順に打ち、画面を見て記録する | 道具は最小。ただし手順と時刻が人によってずれ、根拠を後からたどれない |

## 判断2(決定:A). 規模

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 100チーム(3,000通) | 1回が数分で終わる。同時に送る数(50)より十分多く、強制終了のときに送信中のメールがある |
| B | 1,000チーム(3万通) | 本番に近いが、1回が長く、再送の待ちと重なって30分を超えうる |

## 判断3(決定:A). SMTP の一時エラーの起こし方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 配信の始まりから2分間だけ、30%のメールに 451 を返し、そのあと止める | relay のコードを変えずに済む。再送の間隔(30秒・2分・10分)のうちに届くので、20分ほどで終わる |
| B | 訓練の間ずっと 451 を返し、再送の間隔を設定で短くできるようにする | 上限(5回)を超えて failed になる流れも確かめられる。ただし relay に訓練用の設定を足すことになり、受け入れ基準の外 |

## 判断4(決定:A). 強制終了の二重配信の合否

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 取りこぼしは0であること。二重に届いた数は記録し、同時に送る数(50)以下なら設計どおりとする。超えたら AC-009-09 で直し方を決める | relay の ADR-0002 で受け入れた範囲と一致する。面接では「どこまでなら二重に届きうるか」を数字で説明できる |
| B | 二重配信も0であること | 設計で受け入れた範囲を、訓練で否定することになる。0にするには relay の作りを変える必要がある |

## 判断5(決定:A). 振り返りの単位と書き方

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 訓練ごとに1つのファイル(`docs/postmortems/YYYY-MM-DD-<訓練>.md`)。雛形を `docs/postmortems/README.md` に置く。項目は spec の AC-009-08 のとおり | 1つの障害ごとに時系列と次の手が読める。一般的なポストモーテムの形 |
| B | 5つの訓練をまとめて1つのファイル | 一覧しやすいが、時系列が混ざる |

## 判断6(決定:A). 回数

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 各訓練1回。強制終了だけ3回(二重に届く数は、止めた瞬間に送信中だった数で変わるため) | 負荷試験の学び(ADR-0023 の見直し:比べるときは3回以上)に沿う。合否が数で揺れるものだけ回数を増やす |
| B | すべて3回 | 確かだが、時間がかかる |

## 設計判断(ADR)

判断1〜6を [ADR-0025 障害訓練の方法](../../docs/adr/0025-chaos-drill-method.md) に書いた。

## 結果の残し方

- `docs/postmortems/`:訓練ごとの振り返り(ジョブのログから写した数え、時系列、ログの抜き出し、run の URL)
- `docs/runbook/troubleshooting.md`:障害ごとの気づき方と戻し方(AC-009-10)
- 期待と違う結果は、振り返りの「次の手」に書き、直し方を人間に確認する(AC-009-09)
