# 004 役割と権限:実装計画

spec.md の受け入れ基準をどう作るかを決める。判断が要る点は「判断が要る点」にまとめた。小田の判断を受けてから ADR を書き、tasks.md と実装に進む。

## いまあるもの(002・003 で作った)

- 役割の表(team_member_roles)。1人が複数の役割を持て、代表の行は一意制約で各チーム1人だけ(ADR-0011)
- TeamPolicy:招待、参加申請、選手の管理、名簿の閲覧
- 監査ログ(ADR-0012)と、メールのアウトボックス(ADR-0002)

## 004 で作るもの

```
[代表] メンバー一覧 → メンバーを選ぶ → 役割を変える(本人にメール)
                                     → 代表を交代する(役員だけ選べる。両者にメール)
                                     → 除名する(確認のあと)
[役員] メンバー一覧 → 除名する(代表と他の役員は除名できない)
[代表] チームの設定 → チーム名・競技を変える
[代表] 監査ログ → 誰が・いつ・何をしたかを見る
権限表のすべての操作 × すべての役割を、表を元にした網羅テストで確かめる(AC-004-01)
```

役割はリクエストのたびに DB から読む(キャッシュしない)ので、変更は次のリクエストから効く(AC-004-10)。これは今の作りのままで満たせる。

## 判断が要る点(推奨付き)

### 判断1. 権限表のうち、まだない操作(005・006)の網羅テスト(AC-004-01)

権限表には、お知らせ(005)と既読・配信状況(006)の操作も入っている。API はまだない。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 004 では、いまある操作と 004 で作る操作だけを網羅テストにする。005・006 を作るときに、権限表の行をテストのデータに足す。足していない行があればテストが落ちるようにする(判断7) |
| B | 005・006 の権限の判定だけを先に TeamPolicy に作り、Policy の単体テストで確かめる |

推奨の理由:A は API を作る機能の中で、その権限のテストも書ける。B は使われない判定を先に作ることになり、005・006 の設計(例えばコーチは自分が作ったお知らせだけ)が決まる前に形を決めてしまう。

### 判断2. 「チーム名・競技の変更」と「監査ログの閲覧」を 004 で作るか

権限表にはこの2つがあるが、受け入れ基準は AC-004-01(権限の網羅)だけで、画面や API の基準がない。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 004 で作る。チーム名・競技の変更は、チーム作成(001)と同じ検査で変える。監査ログは新しい順の一覧(100件ずつ)で、日時・操作した人の表示名・操作の種類を日本語で表示する。details の ID は表示しない。spec に受け入れ基準を足す(AC-004-11・12) |
| B | 004 では作らず、権限表から外すか「第2弾以降」とする |

推奨の理由:権限表にある以上、AC-004-01 の網羅テストには API が要る。監査ログは 002 から記録しているが、今は誰も見られず、記録の意味が薄い。どちらも小さい。

### 判断3. メンバー一覧を見られる役割と、表示する項目

役割の変更・除名にはメンバー一覧が要るが、権限表に一覧の閲覧の行がない。

| 案 | 内容 |
|---|---|
| **A(推奨)** | 代表と役員だけが見られる。表示は表示名と役割だけ。メールアドレスは表示しない。権限表に行を足す |
| B | メンバー全員が見られる(連絡網のように) |

推奨の理由:代表と役員は除名のために一覧が要る。コーチや保護者には、今のところ一覧が要る操作がない。メールアドレスは、連絡はお知らせ(005)で送るので画面に出す必要がない(ADR-0003)。

### 判断4. 役割の変更の API の形と、「最後の役割を外す」場合(AC-004-03・06・09)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 役割の一覧をまるごと置き換える(PUT)。代表は含められない(交代は別の操作)。空の一覧は受け付けず、「役割をすべて外すと除名になります」と返す。画面では、すべて外そうとすると除名の確認を出し、確認したら除名の API を呼ぶ |
| B | 役割を1つずつ足す・外す。最後の1つを外すと、確認の印が付いているときだけ除名する |

推奨の理由:A は API の意味が単純で(役割を変える操作と除名は別)、除名の記録・メールも除名の側の1か所で済む。代表の役割は交代でしか動かないので、「代表が自分の代表を外す」(AC-004-06)は API の形で起きない。

### 判断5. 代表を交代するときの役割の付け替え(AC-004-04)

| 案 | 内容 |
|---|---|
| **A(推奨)** | 新しい代表:役員を外して代表を付ける。元の代表:代表を外して役員を付ける。どちらも、コーチ・保護者の役割はそのまま残す |
| B | 新しい代表は役員のまま代表も付ける(役員と代表の両方を持つ) |

推奨の理由:代表は役員のすべての操作ができるので、両方持つ意味がない。両方持つと、後で役割を変えたときに「代表なのに役員の印がない/ある」の扱いが増える。1つのトランザクションで入れ替え、代表が0人や2人の瞬間を作らない。

### 判断6. 除名したメンバーの扱い(AC-004-08)

| 案 | 内容 |
|---|---|
| **A(推奨)** | メンバーの行を消す(役割と選手の紐づけも一緒に消える)。招待リンクから再び申請できる。除名したことは本人にメールしない |
| B | 除名の印を付けて残し、再申請を断る。本人にメールで知らせる |

推奨の理由:受け入れ基準は「直後から見られない」「紐づけが外れる」「監査ログに残す」で、A で満たせる。再申請は承認が要るので、間違って除名したときにも戻せる。メールは受け入れ基準になく、トラブルのもとになる文面を自動で送るより、代表から直接伝えるほうがよい。メールが要るなら spec に足す。

### 判断7. 権限表をテストのデータにする方法(補足)

| 案 | 内容 |
|---|---|
| **A(推奨)** | API のリポジトリに、権限表と同じ並びの表(PHP の配列)を置き、それを元に「操作 × 役割」の全組み合わせで API を呼ぶテストを作る。TeamPolicy のすべての判定が表に入っていることも確かめる(入っていなければ落ちる)。表の先頭に spec.md の権限表への参照を書く |
| B | テストの中で team-ops の spec.md を読んで表を取り出す |

推奨の理由:API の CI には team-ops のリポジトリがないので、B は CI で読めない。A なら表とテストが同じリポジトリにあり、Policy に判定を足したのに表に足し忘れた場合はテストで分かる。

## データ

- 新しい表はない。役割の変更・交代・除名は team_member_roles と team_memberships を変える
- チーム名・競技の変更は teams を変える

## API(案)

| メソッドとパス | 内容 | 権限 |
|---|---|---|
| GET /api/teams/{team}/members | メンバー一覧(表示名・役割) | 代表・役員 |
| PUT /api/teams/{team}/members/{membership}/roles | 役割を置き換える(代表を除く) | 代表 |
| POST /api/teams/{team}/representative | 代表を交代する(役員のメンバーを指定) | 代表 |
| DELETE /api/teams/{team}/members/{membership} | 除名する | 代表、役員(代表と役員は除名できない) |
| PATCH /api/teams/{team} | チーム名・競技を変える | 代表 |
| GET /api/teams/{team}/audit-logs | 監査ログ(新しい順、100件ずつ) | 代表 |

メール:役割の変更(本人)、代表の交代(両者)。どちらもアウトボックス経由で、重複防止キーを付ける(ADR-0002)。

## 画面(案)

- /teams/:teamId/members:メンバー一覧。代表には役割の変更・代表の交代・除名、役員には除名
- /teams/:teamId/settings:チーム名・競技の変更(代表)
- /teams/:teamId/audit-logs:監査ログ(代表)
- チームのホームに、役割に応じて上の画面への導線を足す

## テスト

- 権限表を元にした網羅テスト(AC-004-01)
- 受け入れ基準ごとの Feature テスト、テナント分離、契約テスト、画面のテスト
- E2E:代表が保護者をコーチ兼保護者にする → 本人にメール → 役員を任命して代表を交代する → 役員がメンバーを除名し、除名された人は404

## 関連するADR(判断のあとに書く)

- 役割の変更・代表の交代・除名(判断4〜6)
- 権限表をテストのデータにする(判断1・7)
