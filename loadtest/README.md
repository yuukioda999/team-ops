# 負荷試験

spec 008 と ADR-0023 による負荷試験の道具と結果です。

## 目標(project-brief.md)

| 項目 | 目標 |
|---|---|
| 配信 | 30万通(1万チーム × 30人)を10分以内に送り終える(毎秒500通) |
| 主要な API | p95 が 300ms 以下、失敗 1% 未満 |
| 配信の最中の API | 配信がないときと比べて遅くならない(ADR-0004) |

## 結果

**分かったこと**

- 目標の10分に、約5分届いていない。二重配信と取りこぼしは、どの回も0
- 全体の試験では、**アウトボックスから relay への依頼が最後まで続いている**(760〜792秒)。relay は届いた依頼に追いついて送っている(最後の依頼から最後の1通まで約140秒)。いちばん詰まっているのは、1つの worker が1件ずつ relay に依頼する所
- **予約の公開にも約300秒かかっている**。scheduler が1万件を順に公開するため
- **relay 単体でも 840〜890秒**で、受け取り役の待ち時間を 0ms にしても 810秒とほとんど変わらない。relay の送信は、SMTP の待ち時間ではなく relay の中の処理(1通ごとの接続や DB の更新など)で毎秒350通ほどが上限になっている。依頼の側を速くしても、次は relay が詰まる
- 試験データの作成は 21〜38秒(AC-008-02 の目標 600秒以内)
- API は配信の最中に遅くなる(p95 が 60〜80ms から 220ms ほどへ)が、目標の 300ms 以内。ただし VPS と同じ制限では 1.1秒になり、目標を大きく外れる

### 直し方の段階1:設定だけを変える(2026-11-13)

コードは変えず、API の worker を 1 → 4、notify-relay の同時に送る数(`SEND_CONCURRENCY`)を 50 → 150 にした。詳細は [results/2026-11-13-stage1/](results/2026-11-13-stage1/) にあります。

| 試験 | 直す前(2回) | 段階1(2回) | 目標 |
|---|---|---|---|
| 全体:最後の1通まで | 904・931 秒 | **418・576 秒** | 600 秒 |
| 全体:最後のお知らせの公開 | 303・299 秒 | 186・311 秒 | |
| 全体:relay への最後の依頼 | 760・792 秒 | 252・392 秒 | |
| relay 単体:最後の1通まで | 888・836 秒 | **480・776 秒** | 600 秒 |
| 配信の最中の API の p95 | 223・223 ms | 111・206 ms | 300 ms |
| 二重・取りこぼし | 0・0 | 0・0 | 0・0 |

- 全体の試験は2回とも目標の10分に入った。ただし2回目は 576秒で、余裕がほとんどない
- relay への依頼は大きく縮んだ(worker が4つになったため)。次に長いのは**予約の公開**(186〜311秒、順に公開しているまま)
- relay 単体は 480秒と 776秒で、同じ設定でも大きく揺れた。relay は 500件ずつ取り出し、全部が終わるまで次を取り出さないので、遅い1通が全体を待たせやすい
- 同じ条件の2回で数字が大きく違う。GitHub Actions のマシンの揺れも含まれるので、目標を満たしたと言うには、もう少し余裕が要る

### 直し方の段階2:コードを変える(2026-11-13、効果なし)

段階1の設定のまま、2つのコードの変更を試した。どちらもまだマージしていない。詳細は [results/2026-11-13-stage2/](results/2026-11-13-stage2/) にあります。

- API:予約の公開を、お知らせごとのジョブに分けて worker で並行に行う(team-ops-api #28、[ADR-0024](../docs/adr/0024-publish-scheduled-notices-in-parallel.md))
- relay:取り出した分が全部終わるのを待たず、空いた分だけ続けて取り出す(notify-relay #15)

| 試験 | 段階1(2回) | API の変更だけ(2回) | 両方(2回) | 目標 |
|---|---|---|---|---|
| 全体:最後の1通まで | 418・576 秒 | 746・895 秒 | 602・733 秒 | 600 秒 |
| 全体:最後のお知らせの公開 | 186・311 秒 | 290・415 秒 | 303・315 秒 | |
| 全体:開始から最初の1通まで | 2.6・3.3 秒 | 11.9・13.2 秒 | 8.6・3.0 秒 | |
| relay 単体:最後の1通まで | 480・776 秒 | | 718・628 秒 | 600 秒 |
| 配信の最中の API の p95 | 111・206 ms | 300・330 ms | 204・326 ms | 300 ms |
| 二重・取りこぼし | 0・0 | 0・0 | 0・0 | 0・0 |

- **全体の試験は段階1より遅くなった。** 公開を並行にしても、公開が終わる時刻は早くならなかった(290〜415秒)
- 考えられる理由:公開のジョブと relay へ依頼するジョブが、同じキューと同じ4つの worker を取り合う。キューは積んだ順に取り出すので、先に積んだ1万件の公開ジョブが、あとから積まれる依頼のジョブを待たせる。段階1では、公開は定期実行の側で1件ずつ進み、worker は依頼だけをしていたので、公開と依頼が同時に進んでいた
- 公開が並行でも速くならない理由は、まだ確かめていない(データベースへの書き込みが詰まっている、など)
- relay の変更は、relay 単体で 718・628 秒(段階1は 480・776 秒)。揺れの範囲を出ず、効果は確かめられなかった

## 試験の種類

| 試験 | 流れ | 測ること |
|---|---|---|
| relay 単体 | k6 → notify-relay → 受け取り役 | 30万通を送り終えるまでの時間、受付の p95 |
| 全体 | 1万チームの予約のお知らせ → scheduler が公開 → アウトボックス → worker → notify-relay → 受け取り役 | 予約の時刻から最後の1通までの時間、段階ごとの時間 |
| 配信の最中の API | 全体の試験と同時に、k6 が利用者の主な操作を続ける | 操作ごとの p95 と失敗の割合。配信の前の2分とも比べる |

すべての試験で、受け取り役が受け取った数がちょうど届くはずの数か(二重配信と取りこぼし)も確かめます。

## 動かし方

GitHub の Actions → **Load test** → Run workflow で、試験の種類、規模、受け取り役の待ち時間、CPU とメモリの制限を選びます。結果は成果物(artifact)に残ります。人間が確かめてから `loadtest/results/` にコミットします。

| 置き場所 | 中身 |
|---|---|
| [smtp-sink/](smtp-sink/) | 受け取り役。SMTP で受けて捨て、数えを `GET /stats` で返す(Go の標準ライブラリだけ) |
| [k6/](k6/) | k6 のシナリオ(relay 単体、配信の最中の API) |
| [compose.loadtest.yaml](compose.loadtest.yaml) | 開発用の compose に重ねる設定。API と relay は本番のイメージ、Mailpit の代わりに受け取り役 |
| [compose.vps-limits.yaml](compose.vps-limits.yaml) | デモの VPS と同じ CPU とメモリの制限(3コア・2GB) |
| [collect.py](collect.py) | 受け取り役の数えと、DB の段階ごとの時刻をまとめる |
| [results/](results/) | 試験の結果 |

試験のデータは API の `php artisan loadtest:seed` が作ります。宛先はすべて `loadtest.invalid` で、外には出ません。`APP_ENV` が local・testing・loadtest 以外では動きません。

## 試験の条件で、実際より軽いところ

- **名簿**:試験のデータには選手がいないので、名簿の API は空で返る(AC-008-02 の範囲。選手を足すかは別に決める)
- **配信の前の API**:お知らせはまだ公開されていないので、お知らせの表示と配信状況は呼ばれない。配信の前と最中の比較は、両方にある操作(ホーム・お知らせ一覧・名簿)で行う

## 注意

数字は GitHub Actions のマシン(ubuntu-latest)での値です。本番のサーバーの性能を表すものではありません。目標を満たせなかった場合も、数字をよく見せるために条件を変えず、数字と原因と次の手を記録します。
