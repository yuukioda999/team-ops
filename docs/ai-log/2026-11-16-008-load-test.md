## 2. AIへの指示(要点)

- 優先順位の相談で、AI の推奨(README のあと、VPS より先に負荷試験)を選ぶ
- 計画の判断2〜6に「推奨で」、続けて「全て進めて」
- 直す前の結果を見て、直し方の段階1(設定だけ)に「推奨で進めて」
- 段階2(コードの変更2つ)に「推奨で全て進めて」
- 段階2が速くならなかった報告に「全て推奨で進めて」(API の変更は閉じる、relay の変更は3回ずつ比べて決める、008 は段階1で締める)

## 3. AIの出力

- **道具**
  - 受け取り役(Go、標準ライブラリだけ)
  - k6 の2つのシナリオ(relay 単体、配信の最中の API)
  - 段階ごとの時刻を DB から取り出すスクリプト
  - GitHub Actions の loadtest.yml(規模・待ち時間・VPS の制限・worker の数・同時に送る数・ブランチを選べる)
- **API**:試験データの作成(`loadtest:seed`、試験の環境でだけ動く)と、ログイン済みのセッションの用意
- **測定**:直す前、段階1、段階2、relay の比較。どの回も二重配信と取りこぼしは0
- **段階2のコード**:予約の公開のジョブ化(#28)、relay の連続取り出し(#15)。レビューの指摘を直したうえで測り、どちらも閉じた

## 4. 人間が直したこと

人間は AI の推奨をすべてそのまま採用し、AI の出力を直した箇所はない。人間が気づいて AI に確かめさせたのは次の1件。

- **Vercel からのメール**:人間が「Vercel 触った?」と聞き、届いたメールを見せた。受け取り役のフォルダが Vercel に自動で検出されただけで、AI は何も操作していないことを確かめた

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 進める順番 | VPS の前に負荷試験 |
| 試験の方法 | GitHub Actions で手で実行、受け取り役は自作、1万チームの規模、VPS と同じ制限の回も測る(ADR-0023) |
| 段階1 | worker 1 → 4、同時に送る数 50 → 150。全体の試験は 904〜931秒 → 418〜576秒 |
| 段階2 | 公開のジョブ化と relay の連続取り出し。レビューの指摘はすべて直す |
| 段階2の扱い | 速くならなかったので、どちらもマージしない。ADR-0024 を取り下げにする。008 は段階1の数字で締め、満たせなかった所は「次の手」に残す |
| 結果のレビュー | 21件すべて推奨どおり直す。ADR に「取り下げ」の状態を足す。ADR-0023 は続け、比べるときは条件ごとに3回以上測る |

## 6. AIが間違えた点と学び

- **測らずに「直れば速くなる」と見込んだ**:段階2で AI は「公開を並列にすれば公開が速くなり、全体も縮む」と推奨した。実際は全体が遅くなった。公開のジョブが relay への依頼のジョブと同じキューと worker を取り合うことも、試験のマシンの CPU に空きがあるかも、推奨の前に確かめていなかった(CPU はいまも測っていない)。1件あたりの時間(手元で約13ミリ秒、クエリ約14回)は、結果が出たあとに初めて測った
  - 学び:並列にする前に、1件あたりの時間と、CPU に空きがあるかを測る。同じ worker で別の仕事を回すときは、キューの順番で何が待たされるかを書き出す
- **揺れを知らずに比べた**:段階1の relay 単体の 480秒と 776秒の差を「遅い1通が全体を待たせる」せいと説明し、それを直す変更(#15)を推奨した。3回ずつ比べると、段階1の設定(main)だけで 479〜776秒(5回)揺れ、変更の回(432〜812秒)との差は揺れの中に収まった
  - 学び:直す前に、同じ条件で3回以上測って揺れの幅を知る。揺れより小さい差は「効果」と呼ばない
- **道具の作りで間違えた所**
  - k6 の繰り返しの番号を VU ごとの番号で作り、同じ依頼を重複して送っていた
  - 試験データのチームの ID を大文字で書き、API が 404 を返していた
  - セッションを1件しか保存できていなかった(保存済みの印が残っていた)
- **作業のミス**
  - CI の設定を書き換えるときに、最初に一致した所から置き換えて、別のジョブを消した。以後は actionlint で確かめる
  - 結果のブランチを古い main から作っていた
  - 置き換えのスクリプトでテストのファイルを壊し、戻してからやり直した
- **予想と逆の結果のあと**:マージせずに止めて数字と見立てを報告し、判断を人間に返した。次も、結果が推奨の前提と食い違ったら、進める指示があっても止めて確認する
- **資料に推測を事実として書いた**:結果の README・ADR に、測っていない「CPU に空きがない」「relay の上限は毎秒350通」などを言い切りで書き、レビューで直した。測った数字と見立てを、書き分ける
