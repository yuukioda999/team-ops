## 3. AIの出力

- ADR
  - [ADR-0008 メールのリンクでログイン](../adr/0008-magic-link-login.md)
  - [ADR-0009 チームをURLで指定](../adr/0009-team-scope-in-url.md)
  - notify-relay 側の ADR-0001(外部ライブラリ)と ADR-0002(二重送信の幅と1プロセス前提)
- team-ops-api(Laravel)
  - 主な処理
    - ログイン用リンク(トークンはハッシュだけ保存、15分、1回だけ)
    - 表示名とメールアドレスの変更
    - チームの作成と一覧
    - チームIDの絞り込みと他チームへの404
  - 個人情報の扱い
    - メールアドレスと表示名は暗号化し、検索用にブラインドインデックスを持つ
    - ログと失敗ジョブから個人情報を伏せる
  - notify-relay への依頼
    - アウトボックスと予約型のジョブで送る
    - 毎分の再投入コマンドで取りこぼしを拾う
  - 流量制限、OpenAPI と契約テスト
  - テストは155件
- notify-relay(Go)
  - 受付と重複防止
    - HMAC署名で受け付ける
    - 重複防止キーが同じで内容も同じなら200、内容が違えば409
  - 送信
    - SMTPで送る
    - 失敗したら5段階の間隔で再送する
    - 停止時は中断した送信を戻す
  - 宛先の扱い:最終状態でアドレスを消し、ログはハッシュの先頭だけ
  - デモモード:実在のアドレスには送らない
- team-ops-web(React)
  - 画面
    - ログイン、リンクの確認
    - 表示名の登録
    - チームの作成、切り替え
    - アカウント設定
  - URLからトークンを消す
  - 本番用 nginx(セキュリティヘッダー、トークンをログに残さない)
  - テストは54件
- team-ops
  - compose(全サービスとヘルスチェック)、README のログイン手順
  - E2E テスト(Playwright)
    - CI の smoke で、`make up` 相当の環境に対して毎回動く
    - ログイン用リンクは Mailpit から読む

## 4. 人間が直したこと

コードを人間が直接書き換えた箇所はない。人間が直したのは、進め方とAIの提案の方向。

- **レビューの進め方**
  - 人間が出した案:AIが自分で開発とレビューを続け、人間は判断だけを行う。AIはこれに合わせて、レビューで止めない進め方を示した
  - 人間の判断:それでは判断すべきところを判断できないとして、レビューのたびに人間に指摘を示して止める元の流れに戻した
  - 記録の仕方:AIのレビュー結果を人間のレビューとして記録する案も出たが、事実どおり「AIレビューの指摘」と「人間の判断」を分けて記録することにした。CLAUDE.md の手順5はこの合意に合わせて書いた
- **レビュー指摘の採否**
  - 各レビューで、指摘ごとに人間が直すかどうかを決めた
  - 今回はすべて推奨どおりに直す判断だった
  - 経緯は各プルリクエストに記録した
- **ログイン用リンクの開き方**
  - リンクを開いただけではログインせず、ボタンを押したときにだけトークンを使う(ADR-0008)
  - 人間が意味を確認してから承認した。メールソフトのリンク先読み込みでトークンが使われてしまうのを防ぐため

## 6. AIが間違えた点と学び

AIの誤りの多くは、テストやCI、実際のブラウザでの確認で見つかった。

- **間違った理由で通るテスト**
  - 何が起きたか:Laravel の Feature テストが、認証ガードとセッションのキャッシュ、JSONリクエストでクッキーが送られないことにより、本来の理由とは違う理由で通っていた。たとえば30日の期限切れテストは、期限を確かめていなかった
  - 学び:テストを書いたら、一度わざと実装を壊して落ちることを確かめる
- **照合順序の見落とし**
  - 何が起きたか:MySQL の照合順序(大文字小文字を区別しない)で、重複防止キーと宛先の参照値が一意にならない問題があった。ローカルの MariaDB では気づけず、CI の MySQL で見つかった
  - 学び:キーとして比べる列は、最初から utf8mb4_bin にする
- **重複防止キーの衝突**
  - 何が起きたか:API のDBだけを作り直すと、トークンのIDが再び1から始まり、notify-relay が409を返した
  - 対応:キーにハッシュの一部を足した(api #9)
  - 学び:別のサービスに渡すキーは、片方のDBを作り直しても一意になるように作る
- **本番用 nginx の設定**
  - 何が起きたか:次の3つは、本番用の nginx を通して実際のブラウザで確かめるまで分からなかった
    - Referer からトークンがアクセスログに残る
    - Referrer-Policy を no-referrer にすると、同じオリジンへのリクエストでセッションが使えなくなる
    - CSP が Vite の埋め込みフォントを止める
  - 学び:セキュリティヘッダーは、本番と同じ構成で画面を通して確かめる
- **Go の依存の検証値**
  - 何が起きたか:作業環境では Go のモジュールプロキシに接続できなかった。自作のプロキシで作った go.sum の検証値が公式と違い、CI で見つかった
  - 学び:作業環境の制約で作った回避策は、CI で必ず検証する
- **自分の作業環境を止めた**
  - 何が起きたか:プロセスを名前で一括停止したときに、自分のシェルまで止めた
  - 学び:停止はスクリプトにまとめ、対象を絞る

## T30 最終レビュー

- **レビューの進め方**
  - reviewer と security-reviewer に、4リポジトリの main をまとめて見させた
  - 深刻度「高」の指摘は1件あった。どちらのエージェントも、セキュリティ上の重大な問題は見つけなかった
- **AIの見落とし**
  - 何が起きたか:`make test-api`(コンテナの中で API のテストを動かす)は、155件中59件が失敗していた
  - 原因:コンテナに入っている env/api.env の値が、phpunit.xml の値より優先されていた。CI はコンテナを使わずにテストするので気づけなかった
  - さらに:phpunit.xml の `force` だけでは足りなかった。Laravel は `$_SERVER` を先に読むので、`<server>` でも強制する必要があった
  - 学び:README に書いた手順は、CI と別の方法で動くなら、その方法でも一度動かす
- **E2E テストでの確認**
  - T29 の E2E テストで、Docker の compose 環境を使い、ログインからチームの切り替え、メールアドレスの変更までを、CI で毎回通している
  - 一方、デモモードで実在のアドレスを入れると500になることは、このレビューまで見つからなかった。テストが `.invalid` のアドレスしか使っていなかったため
- **人間の判断を待たずに直したもの**
  - 小田の指示(T31まで進める)に基づき、AIは確実な不具合と資料の誤りだけを直し、CI が通ってからマージした
  - 残りの14件は判断を推測せず、推奨を付けて [review-t30.md](../../specs/001-account-and-team/review-t30.md) に残した。月曜に小田が判断する

## 判断を反映した変更のレビュー

- **進め方**
  - 小田の指示で、4つのプルリクエストを reviewer と security-reviewer で見た
  - 指摘は20件。小田は「全部推奨で」と判断し、AIはそのとおりに直した
  - 内容は [review-t30.md](../../specs/001-account-and-team/review-t30.md) の4に記録した
- **AIの誤り**
  - **マージの順番の誤り**:プルリクエストに「API はどの順でもよい」と書いたが、誤りだった。team-ops を先にマージすると、宛先の制限が外れる
  - **設定名の不揃い**:API に新しい設定名を入れたのに、notify-relay は古い名前しか読まないままだった。二重の安全策の片側が、何も知らせずに外れうる状態だった
  - **テストの漏れ**:鍵の検査が、生の文字列で書いた鍵と `APP_PREVIOUS_KEYS` を見ていなかった。検査のテストも補助クラスしか見ておらず、配線を外しても通っていた
  - **書き換え漏れの検証**:テストが本当に検査をしているかを確かめるために配線を外したとき、pint が書き換えた行を sed で消せていなかった。その結果、外れていない状態でテストが通り、誤った確認になりかけた。消せたことを grep で確かめてから実行し直した
- **学び**
  - 設定名を変えるときは、同じ設定を読むすべてのリポジトリを検索する
  - 検査のテストは、補助の関数ではなく実際の経路(リクエスト、コンテナからの解決)で確かめる
  - 依存のある複数のプルリクエストは、どれを先にマージしても壊れないかを確かめてから順番を書く
