## 2. AIへの指示(要点)

- 「002 はとりあえず一通り作ってくれる?」
- AIは「判断を推奨で仮決定して止まらずに進める」案を出した。人間はこれを採らず、「これまで通りの進め方で」と指示した。判断が要る点で止まり、選択肢と推奨を示す進め方のまま進めた
- plan の判断9件に「全部推奨で」、レビューの指摘15件にも「全部推奨で」
- 返答は日本語で書くよう、何度か指示があった(AIが英語で報告したため)

## 3. AIの出力

- **plan.md**:判断が要る点を9件、選択肢と推奨を付けて示した。例えば、未ログインで招待リンクを開いた人をログイン後に申請画面へ戻す方法、トークンの持ち方、役割の持ち方、TeamPolicy の時期、監査ログの時期など
- **ADR**:3件(招待リンクと戻り先、役割の表と TeamPolicy、監査ログ)
- **spec の追加**:AC-001-19、AC-002-16〜18
- **API**:招待リンク、参加申請、承認・却下、自動取り消し、削除、ログイン後の戻り先、監査ログ、OpenAPI。テストは237件
- **画面**:招待(URL・QR)、招待リンクから開く画面と申請フォーム、承認待ちの一覧、最初の画面の申請状況。テストは80件
- **E2E**:代表と保護者を別々のブラウザで動かし、リンクの発行 → 申請 → 承認までを通す。ログイン用のメールを別のタブで開いても申請画面に戻ることも確かめる

## 4. 人間が直したこと

コードを人間が直接書き換えた箇所はない。人間が直したのは、進め方と判断。

- **進め方**:AIが出した「推奨で仮決定して止まらずに作る」案を退け、判断のたびに止める元の流れを続けさせた
- **判断**:plan の9件とレビューの15件は、すべて推奨どおりに決めた(レビューのうち、却下ボタンの確認の1件は推奨どおり直さなかった)
- **言語**:AIが英語で報告したときに、日本語で書くよう指示した

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 1 | ログイン後の戻り先を、ログイン用のリンクと一緒に API が覚える(AC-001-19) |
| 2 | 招待リンクは、照合用のハッシュと暗号化したトークンを持ち、何度でも見せ直せる |
| 3 | 役割は別の表に持つ(1人が複数の役割を持てる) |
| 4 | TeamPolicy を 002 で作る(004 の予定を前倒し) |
| 5 | 申請の表示名はアカウントの表示名にする |
| 6 | ひとことは暗号化し、最終状態で消す。申請の記録は30日後に消す |
| 7 | 却下・取り消しのあとも再申請できる |
| 8 | 監査ログの最小限の仕組みを 002 で作る |
| 9 | QR コードはブラウザで作る |
| レビュー | 14件を直した。例えば、Controller のクエリを UseCase に移す、1人1チーム1日3回まで(AC-002-18)、申請画面の注意書き |

## 6. AIが間違えた点と学び

- **判断1を、ADR を書く段階で形を変えた**
  - 人間が決めたのは「ログイン用メールのリンクに戻り先を含める」だった。AIは ADR を書くときに「メールには含めず、API が保存する」形に変えた。目的は同じで、メールの URL も短くなる
  - 変えたことはプルリクエストで伝えたが、ADR の選択肢の表を直し忘れ、レビューで食い違いを指摘された
  - 学び:決めた内容を実装の段階で変えるときは、変える前に人間に確認する。変えたら、関係する資料をすべて直す
- **Controller にクエリを書いた**
  - CLAUDE.md の「Controllerから直接クエリを書かない」に反していた。レビューで指摘された
  - 学び:書き終えたら、CLAUDE.md の設計ルールを1つずつ確かめる
- **MySQL と MariaDB の違い**
  - 監査ログの JSON 列のキーの順番を、テストが前提にしていた。作業環境の MariaDB では通り、CI の MySQL で落ちた
  - 学び:JSON の中身は順番に依存しない比べ方で確かめる
- **リポジトリをまたぐ型の変更**
  - API の応答の role を roles(リスト)に変えると、API だけをマージした状態では画面の役割の表示が壊れる。これはレビューで指摘された
  - 学び:リポジトリをまたぐ変更では、どれを先にマージしても壊れないかを先に確かめ、壊れるなら続けてマージする
- **英語で報告した**
  - 何度も指摘を受けた。報告は日本語で書くことを徹底する
