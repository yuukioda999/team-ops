## 6. AIが間違えた点と学び

- **訓練の道具の最初の版に、3つの誤りがあった**(CI で1回目を動かして見つけ、直した)
  - 「全員の結果がそろうまで待つ」を、お知らせの公開の前から数えていた。公開の前は待つものが0件なので、恒久エラーの訓練は公開の前に「終わった」と判定し、障害を止めていた
  - API を止める訓練で、「1割を送ったら止める」としていた。3,000通は約10秒で送り終わるので、止めたときには結果がすでに API に届いていて、確かめたいことが起きなかった
  - 二つのスキーマの文字列をつなぐクエリが、照合順序の違いで失敗した。エラーの中身を出していなかったので、原因を探すのに1往復かかった
  - 学び:訓練の道具は、「障害が、確かめたい処理の最中に起きたか」を時系列で確かめてから結果を読む。時刻はログに残す作りにしておいてよかった
- **ログの数え方の誤り**:notify-relay のログは JSON なのに、テキストの形だけを探していて、警告を0件と出していた。「どう気づいたか」を書く前に気づいて直した
- **手順書に事実でないことを書きかけた**:強制終了の戻し方に「お知らせの文面は、2通届く前提で書かれている」と書いたが、確かめると文面にそうした注意はなかった。消して、振り返りの「次の手」に回した
  - 学び:ADR に「〜する前提で作る」とあっても、作ったかどうかはコードで確かめる
- **強制終了の合否の数え方**:最初は「強制終了の直前に sending だった数」を二重配信の上限にしていた。sending は取り出した分(最大500)で、送ったかどうかを表さないので、判断4のとおり「同時に送る数(50)」で判定するように直した
- **判定が「最後の状態」しか見ていなかった**:レビューで、障害が空振りしても「期待どおり」になる作りだと指摘された。最初の版の誤り(公開の前に終わる、API を止めるのが遅い)を自分で見つけたのに、それを判定に入れていなかった
  - 学び:訓練の判定は、まず「当たった」ことを確かめる。判定は単体テストで、空振りと打ち消し合いの場合を確かめる
- **差し引きで数えていた**:取りこぼしを「届くはずの数 − 届いた数 − 失敗の数」で出していた。取りこぼしと「失敗と記録したのに届いた」が1件ずつあると、0と出る。宛先ごとに並べる形に直した
- **送り直しの間隔を、定数のまま書いた**:手順書に「30秒・1分・2分…」と書いたが、送り直しは毎分の定期実行が拾うので、実際は約1・1・2・5・10・30分だった。24時間で諦めることも書いていなかった
- **見ていない画面を、見たように書いた**:訓練では画面を起動していないのに、振り返りに「画面に出る」と書いていた。見立てと分かるように直した
- **決まった直しが、実装の前にできないと分かった(判断 E)**:本文の最後に注意書きを足すと、お知らせの本文の上限(2,000文字)と notify-relay の受け付けの上限(2,000文字)が重なり、長いお知らせが送れなくなる。推奨を出す前に、上限を確かめていなかった。実装せずに止め、決め直しを人間に確認する
- **決まった直し方では足りなかった(F)**:受け付けの deadlock を「やり直す」で直すと決まったが、同時に走らせるテストを作ると、3回のやり直しでも20回中で失敗が残った。推測で回数を増やさず、原因(既定の分離レベルの、索引のすき間のロック)を直す案を足し、ADR を「提案中」にして人間に返した
- **コミットの作者を、直前のコミットから取っていた**:コミットの作者のメールアドレスを「直前のコミットの作者」から取る書き方をしていた。直前が Dependabot のマージだったので、API の1コミットが Dependabot の作になった。レビューで見つかり、作り直した。以後はアドレスを決め打ちにする
- **`--now` が、送り直しの前提を崩すことに気づいていなかった**:「送るのは1つだけ」は、送り直しの間隔が notify-relay の待ち時間より長いことに頼っていた。`--now` はそれを崩し、送った記録を「諦めた」で上書きしうる。レビューで指摘され、結果を書くのを予約が有効なジョブだけにした
- **確かめていない仕組みで説明した(F)**:READ COMMITTED の案は、手元の MariaDB で再現したテストを根拠にした。CI の MySQL 8.4 では同じテストで deadlock が起きず、訓練で起きた deadlock の相手は確かめられていない。人間は「推奨で」と決めたが、根拠が足りないと分かったので、いったん決め直しを求めた。その後、訓練のジョブのログに MySQL の deadlock の記録を出すようにし、MySQL 8.4 でも相手が取り出しだと確かめた
  - 学び:本番と違うデータベースで再現した結果を、本番の原因の説明に使わない。説明の前に、本番と同じものでの記録(deadlock の記録)を取る
- **測り直して新しい不具合が見えた**:手順どおり `--now` で送り直した回で、1件だけ約6分遅れた。エラーの行をジョブのログに出すようにして、notify-relay の受け付けが MySQL の deadlock でやり直さずに失敗していることを確かめた
