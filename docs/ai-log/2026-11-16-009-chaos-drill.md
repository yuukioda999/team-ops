## 2. AIへの指示(要点)

- 「これからやること」の2つ(障害訓練と振り返り、Dependabot の仕分け)に「これ進めて」
- 計画の判断1〜6と、Dependabot の扱い、見つかった監視の不具合の直し方に「推奨でいいです」

## 3. AIの出力

- **spec と計画**:5つの訓練(SMTP の一時エラー・恒久エラー、notify-relay の停止・強制終了、API の停止)と、受け入れ基準 AC-009-01〜11。判断1〜6を選択肢と推奨で示した
- **道具**:`chaos/`(compose の設定、障害を起こして戻す drill.sh、宛先ごとに数えて照らし合わせる report.py)、`chaos.yml`、`make drill`
- **訓練**:5種類(強制終了は3回)。すべて期待どおり。強制終了では 46・47・47通が二重に届いた(基準の50通以下)
- **振り返り**:訓練ごとに5つと、雛形
- **手順書**:障害ごとの気づき方と戻し方
- **Dependabot**:13件を仕分けた。10件をマージし、MySQL 26.10(バックアップからの戻しが失敗)と PHP 8.5(本番・CI とずれる)は閉じた。Alloy の版上げは、下の不具合を直してから確かめ直す

## 4. 人間が直したこと

人間は AI の推奨をすべてそのまま採用し、AI の出力を直した箇所はない。

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 訓練の方法 | GitHub Actions、100チーム、451 は2分だけ、強制終了は取りこぼし0・二重は50通以下で合格、訓練ごとの振り返り、強制終了だけ3回(ADR-0025) |
| Dependabot | 10件マージ、MySQL 26.10 と PHP 8.5 は閉じて以後の提案を止める、Alloy は不具合を直してから |
| 監視の不具合 | socket-proxy でネットワークの読み取りを許可し、deploy-check が Alloy のエラーをすべて拾うようにする |
| 振り返りの「次の手」 | 確認待ち(notify-relay の起動から送り始めるまでの待ち、二重に届いたメールの扱い) |

## 6. AIが間違えた点と学び

- **訓練の道具の最初の版に、3つの誤りがあった**(CI で1回目を動かして見つけ、直した)
  - 「全員の結果がそろうまで待つ」を、お知らせの公開の前から数えていた。公開の前は待つものが0件なので、恒久エラーの訓練は公開の前に「終わった」と判定し、障害を止めていた
  - API を止める訓練で、「1割を送ったら止める」としていた。3,000通は約10秒で送り終わるので、止めたときには結果がすでに API に届いていて、確かめたいことが起きなかった
  - 二つのスキーマの文字列をつなぐクエリが、照合順序の違いで失敗した。エラーの中身を出していなかったので、原因を探すのに1往復かかった
  - 学び:訓練の道具は、「障害が、確かめたい処理の最中に起きたか」を時系列で確かめてから結果を読む。時刻はログに残す作りにしておいてよかった
- **ログの数え方の誤り**:notify-relay のログは JSON なのに、テキストの形だけを探していて、警告を0件と出していた。「どう気づいたか」を書く前に気づいて直した
- **手順書に事実でないことを書きかけた**:強制終了の戻し方に「お知らせの文面は、2通届く前提で書かれている」と書いたが、確かめると文面にそうした注意はなかった。消して、振り返りの「次の手」に回した
  - 学び:ADR に「〜する前提で作る」とあっても、作ったかどうかはコードで確かめる
- **強制終了の合否の数え方**:最初は「強制終了の直前に sending だった数」を二重配信の上限にしていた。sending は取り出した分(最大500)で、送ったかどうかを表さないので、判断4のとおり「同時に送る数(50)」で判定するように直した
- **見つけたこと**:Dependabot の仕分けで構成のチェックのログを読み、本番の構成で監視がコンテナのログを集められていない不具合を見つけた。毎日のチェックは特定の文言しか探しておらず、ずっと成功になっていた
  - 学び:「失敗しないこと」を確かめるチェックは、知っている失敗の文言だけを探すと、知らない失敗を見逃す。エラーはすべて拾い、例外だけを外す
