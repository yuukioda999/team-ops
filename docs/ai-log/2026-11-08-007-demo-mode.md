- **API**
  - デモチームを架空のデータから作る(代表・役員・コーチ2・保護者20、選手20、参加申請2、お知らせ3)

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 1 | デモチームは架空のデータの定義(コード)から、ログインのたびに作る |
| 2 | 1時間ごとに、作成から24時間を過ぎたものを消す |
| 3 | 送信されたメールは、API が Mailpit の API に宛先のドメインで問い合わせる |
| 4 | チームごとに架空のユーザーを作り、役割の切り替えはそのユーザーへのログインし直し |
| 5 | デモユーザーかどうかではなく、デモモードかどうかで止める |

## 6. AIが間違えた点と学び

- **メールの削除を「1回だけ、うまくいく前提」で書いていた(レビュー1・14)**
  - Mailpit が止まっていたり、削除のあとに配信が届いたりすると、そのメールは無期限に残る作りだった。コードのコメントには「やり直せない」と自分で書いていたのに、そのままレビューに出した
  - 学び:「消す」処理は、失敗と遅れて届くものを前提にして、後から回収できる形にする。自分のコメントに「できない」と書いたら、それは直すべき点の印
- **回数制限を IPv6 で考えていなかった(レビュー2)**
  - アドレス全体で数えていたので、1つの回線で何度でも作り直せた
  - 学び:IP で数える制限は、IPv6 では /64 を1つの単位にする
- **ルートの外で認証を確かめたときに、共通のエラーの形を通していなかった(レビュー3)**
  - 404 を先に返すために auth:sanctum の外で確かめたところ、期限切れの理由(`demo_expired`)が付かなくなった
  - 学び:共通の仕組み(ミドルウェア・例外の変換)を外れるときは、それが返していたものをすべて自分で返しているか確かめる
- **受け入れ基準のテストが1つ抜けていた(レビュー4)**
  - AC-007-18 のテストがなかった
  - 学び:レビューに出す前に、spec の AC の ID をすべてテストの中から検索する
- **決まりを守っていなかった(レビュー5・13)**
  - 画面で API の型を手で書いていた。また ADR では「デモモードかどうか」で止めると決めたのに、画面は「デモユーザーかどうか」で判定していた
  - 学び:ADR の決定の文と、CLAUDE.md の決まりを、実装のあとにもう一度読み合わせる
- **指摘の直し方が、別の受け入れ基準とぶつかった(レビュー6)**
  - セッションの行を消すと決めたが、消すと AC-007-08(期限切れを伝える)ができなくなった。テストが落ちて気づき、行は残して IP・ブラウザの情報とユーザーだけを消す形にした。その旨を小田に報告した
  - 学び:直し方を推奨するときに、同じデータを使っている受け入れ基準がないか先に調べる
- **ADR に、実際には使えない条件を書いていた(レビュー9)**
  - tenant_ref は暗号化した中身の一部で検索できないのに、ADR の「削除」に tenant_ref で消すと書いていた。推奨も「実装を ADR に合わせる」と出していて、直す段になって初めてできないと分かった
  - 学び:ADR に条件を書くときは、その列が検索できるか(暗号化していないか)をスキーマで確かめる
- **E2E で、001 と同じ手順を省いていた**
  - ログインのリンクを開いたあとの「ログインする」のボタンを押さずに、次の画面を待っていた。CI で一度落ちた
  - 学び:同じ流れの既存のテストがあれば、手順をそのまま使う(flows.ts の関数にする)
