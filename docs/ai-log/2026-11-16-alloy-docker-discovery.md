# 監視の不具合:Alloy がコンテナを見つけられなかった(team-ops #31)

## 1. タスク

- 見つけた経緯:Dependabot の PR を仕分けるときに、毎日の構成チェック(deploy-check)のログを読んで見つけた
- ADR:[ADR-0022 デモ環境のサーバーと公開の方法](../adr/0022-demo-server-and-deploy.md)(2026-11-16 追記)
- 手順書:[monitoring.md](../runbook/monitoring.md)
- プルリクエスト:team-ops #31

## 2. AIへの指示(要点)

- 「これ進めて」(Dependabot の仕分け)の途中で AI が不具合を報告し、直し方に「推奨でいいです」
- 「レビュー進めて」、指摘に「全て推奨で直して」、「推奨で直して、あと他の対応もレビューして」

## 3. AIの出力

- 原因:Alloy のコンテナの検出はネットワークの情報も読むが、Docker の窓口(docker-socket-proxy)がネットワークの読み取りを許可しておらず、403 で断っていた。Alloy はコンテナを1つも見つけられず、ログを1行も集めていなかった
- 直し方:窓口でネットワークの読み取り(GET)を許可する。使う許可(PING・VERSION)を明示し、使わない EVENTS を閉じる
- 確かめ方:deploy-check で、Alloy 自身の状態から、アプリのサービス(api・api-worker・api-scheduler・notify-relay・web・caddy)がすべて対象に入り、ログを読んだ行数が0より多いことを確かめる。そのあと、ほかのエラーが出ないことを見る

## 4. 人間が直したこと

人間は AI の推奨をすべてそのまま採用し、AI の出力を直した箇所はない。

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 直し方 | ネットワークの読み取りを許可し、チェックを強める |
| 窓口から秘密やファイルまで読める問題(判断 C) | ADR に事実として書き、読めるパスを絞れる窓口への入れ替えは別の PR で行う |

## 6. AIが間違えた点と学び

- **毎日のチェックが、知っている失敗の文言だけを探していた**:公開の準備のときに AI が書いたチェックは `permission denied` と `error while listing containers` だけを探していて、403 は当たらなかった。毎日「成功」になっていた
  - 学び:「失敗しないこと」を確かめるチェックは、知っている失敗の文言を探すだけでは、知らない失敗を見逃す
- **エラーが消えたことを「直った」とした**:最初の直しでは、403 のエラーが消えたことだけで直ったとしていた。レビューで「ログが集まっている証拠がない」と指摘された
  - 学び:直ったと言うには、期待する動きが起きている証拠を見る。エラーが無いことは証拠にならない
- **証拠の数え方が甘かった**:次の直しで「見つけたコンテナ7、読んだログ123行」を証拠にした。再レビューで、7 はコンテナではなく対象(ポートやネットワークごと)の数で、確かめた時点ではアプリのコンテナがまだ起動していなかった見込みが高いと指摘された。アプリのサービスの名前がすべて対象に入るまで待つ形に直した
  - 学び:証拠は「何が」そろったかで確かめる。数が0より多い、では足りない
- **窓口を「読むだけ」と書いていた**:ADR-0022 には「コンテナの一覧とログを読むことだけを許した窓口」と書いていた。実際は、ほかのコンテナの環境変数(秘密)やファイル(DB のデータ)まで読める。事実どおりに書き直した
