## 2. AIへの指示(要点)

- 「いまの全体の進捗は?」のあと「進めて」。AI は判断7件が未決のため推奨どおりでよいか確認し、「全部推奨で」
- 判断8(003 からの引き継ぎ)は、AI が実装の前に確認し「一緒に外す」
- 「レビューして」で reviewer と security-reviewer を動かし、指摘15件に「全部推奨で」

## 3. AIの出力

- **001 の不具合**:未ログインで Accept を付けずに API を開くと 500 になる不具合を、未ログインの人を移動させない設定で直した。修正前に失敗するテストを先に書いた
- **plan.md**:判断が要る点を7件、選択肢と推奨を付けて示した(まだない操作の網羅テスト、チーム名・監査ログを作るか、メンバー一覧の範囲、役割の変更の形、代表の交代の付け替え、除名の扱い、権限表の置き場所)
- **ADR**:2件(役割の変更・代表の交代・除名、権限表をテストのデータにする)
- **API**:メンバー一覧、役割の変更(本人にメール)、代表の交代(両者にメール)、除名、チーム名・競技の変更、監査ログの閲覧。権限表を元にした網羅テスト。テストは413件
- **画面**:メンバー一覧、メンバーの管理(役割・交代・除名)、チームの設定、監査ログ。テストは127件
- **E2E**:役割の変更 → 代表の交代 → 除名 → 監査ログまでを通す

## 4. 人間が直したこと

コードを人間が直接書き換えた箇所はない。人間が直したのは判断。

- plan の7件、判断8、レビューの15件は、すべて推奨どおりに決めた
- レビューのうち、1件は文書で対応(代表は空の役割でもよい、と ADR を直す)、1件は直さない(SQLite では確かめられないロックのテスト)と決めた

## 6. AIが間違えた点と学び

- **判断が要る点を、tasks.md に「決めたこと」として書いた**
  - 003 から引き継いだ「保護者を外したときの紐づけ」を、AI が tasks.md に書き込んだあとで判断が要ることに気づき、実装の前に人間に確認した
  - 学び:引き継いだ項目も、plan の判断として選択肢と推奨を付けて示す。文書に書く前に確認する
- **「進めて」を判断の承認と取らなかった**
  - 判断7件が未決のまま「進めて」と言われたため、推奨どおりでよいか確認した。推測で進めないという決まりどおり
- **ULID のチームを監査ログの対象(数値の列)に入れた**
  - SQLite では通り、MariaDB のテストで落ちて気づいた。監査ログの部品で数値でない ID を拒むようにした
  - 学び:DB を使うテストは CI と同じ MySQL 系でも動かす(CLAUDE.md の決まり)
- **権限の確かめ直しが、操作によってそろっていなかった(S1)**
  - 代表の交代だけがロックのあとで権限を確かめ直していて、役割の変更と除名にはなかった
  - 学び:同じ種類の操作(役割・所属を変えるもの)は、ロックの順と判定の場所をそろえる
- **網羅テストが行ごとに API を1つしか呼んでいなかった**
  - 「すべての操作」を「行ごとに代表の1つ」と狭く読んでいた。テスト名に、まだ確かめられない AC-004-02 も入れていた
  - 学び:受け入れ基準の言葉どおりに範囲を取る。テスト名の ID は、その基準を実際に確かめているものだけに付ける
- **ADR と実装の食い違い**
  - 「空は 422」と ADR に書いたのに、実装では代表なら空でも受け付けていた。レビューで指摘され、人間の判断で ADR を直した
  - 学び:実装で決めた細部が ADR と違ったら、その場で人間に確認する
