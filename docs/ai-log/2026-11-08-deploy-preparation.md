## 2. AIへの指示(要点)

- 「デモモードはサーバーどうするの?」に続けて、「アクセスは少ない。契約はこちらで手配するので、環境を準備できたら教えて。設定も一緒に進めたい。メールサーバーは?」
- サーバーの選択肢に「はい推奨で」(さくらのVPS 2GB、画面も VPS から配る、`demo.freie.jp`、まず月払い)
- 公開の方法の4つに「推奨で」(FrankenPHP、Caddy、最初は手でデプロイ、毎日のバックアップと Grafana Cloud)
- 「進めてください」で準備に入る。「レビューして」に続けて、22件の指摘に「すべて推奨で直して」
- 「マージして」
- 翌日に「VPSは必須? 現在の状態でもアピールにならない?」と聞き、AI の推奨どおり VPS の契約は後回しにした

## 3. AIの出力

- **ADR-0022**:サーバー、画面の配信、FrankenPHP、Caddy、GHCR、手で行うデプロイ、バックアップ、監視
- **API**:本番のイメージを FrankenPHP にした(root 以外で動かす)。定期処理のログをコンテナのログに出す設定を足した
- **画面**:Caddy の後ろで、利用者の本当の IP を受け取る。信頼するのは決めた相手の X-Forwarded-For だけ
- **3つのイメージ**:main でコミットのハッシュのタグを付け、GHCR に置く
- **deploy/**
  - 本番の Compose(Caddy、web、api、worker、scheduler、relay、MySQL、Mailpit、Alloy、docker-socket-proxy)
  - `init-env.sh`(秘密情報を乱数で作る)
  - `deploy.sh`(失敗したら前の版に戻す、`--rollback`)
  - バックアップと戻し
- **手順書**:初期設定から公開まで、デプロイ、バックアップ、監視、証明書、困ったとき
- **deploy-check.yml**:同じ構成を CI で起動し、外から HTTPS で次を確かめる。毎日動かす
  - 007 の E2E
  - 外に出ているのが Caddy だけ
  - ログに Cookie が出ない
  - IP の受け渡し
  - データを変えてから戻せる

## 4. 人間が直したこと

コードを人間が直接書き換えた箇所はない。人間が直したのは判断。

- サーバー・公開の方法の選択肢と、レビューの22件は、すべて推奨どおりに決めた
- **VPS の契約を後回しにした**:AI は公開を前提に「契約してください」と案内していた。人間が「VPS は必須か」と問い直したことで、AI は次の比較を示した
  - VPS が無くても CI で本番相当を毎日確かめている
  - 面接官が実際にデモを触ることは多くない
  - 月額の費用と運用の手間がかかる

  人間がその推奨(README・負荷試験・障害訓練を先に)を選んだ

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| サーバー | さくらのVPS 2GB(Ubuntu 24.04)、まず月払い。画面も VPS の nginx から配る。`demo.freie.jp` |
| 公開の方法 | FrankenPHP、Caddy で HTTPS、GitHub Actions で作って GHCR に置く、最初は `deploy.sh` を手で実行 |

## 6. AIが間違えた点と学び

- **ADR に、無い仕組みを前提にした決定を書いた**
  - 監視について「今の OpenTelemetry でトレースも送る」と書いた。実際には、API と relay にトレースを出す仕組みはまだ無かった。実装の段階で気づき、ログとサーバーの指標に範囲を絞って ADR を直した
  - 学び:「今の〇〇をそのまま使う」と書く前に、その〇〇がコードにあるかを検索する
- **workflow の書き換えで、別の job を壊した**
  - CI の `image:` の job を置き換えるつもりで、文字列の最初の `image:`(test の job の `image: mysql`)から後ろを置き換えた。test の job が消えて CI が動かなくなった。actionlint で原因を見つけた
  - 学び:YAML は文字列で置き換えず、範囲を確かめてから直す。直したら actionlint を通す
- **ログの中の秘密を、リクエスト側しか見ていなかった(レビュー2)**
  - Caddy のログから Cookie・Authorization・token は消した。しかし、応答の Set-Cookie(ログインのセッション)が残り、Grafana Cloud に送られる設定だった
  - 学び:ログの伏せ字は、リクエストと応答の両方の欄を一覧にして確かめる
- **フレームワークの動きを確かめずに、ログの経路を決めた(レビュー3)**
  - `schedule:work` が各コマンドの出力を捨てることを知らず、定期処理のアラートが一度も鳴らない設定にしていた
  - 学び:アラートを決めたら、そのログが実際に届くことを CI で確かめる(今は deploy-check で確かめている)
- **戻す仕組みが、いちばん使う場面で動かなかった(レビュー1)**
  - `--rollback` は、デプロイが失敗した直後に、1つ古すぎる版に戻る作りだった
  - 学び:戻す仕組みは「失敗した直後」の場面で考える。偽の docker を使ったテストで、成功・失敗・戻しの流れを確かめてから出す
- **広すぎる信頼(レビュー9)と、強すぎる権限(レビュー4)**
  - X-Forwarded-For を Docker の範囲全体から信頼していた。また、監視の Alloy に Docker のソケットとホストの `/` を渡していた
  - 学び:信頼する相手と渡す権限は、必要な1つに絞る(アドレスを固定する、読むだけの窓口を通す)
- **GHCR の権限は確かめていなかった**
  - 画面のイメージだけ、GHCR に置くときに「denied」で拒否された(API と relay は置けた)。リポジトリとパッケージの権限は、GitHub の画面で人間が設定する必要がある。公開の手順0に入れてある
