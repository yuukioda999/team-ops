## 2. AIへの指示(要点)

- 「続けて」で 005 を開始。AI は plan の判断7件を選択肢と推奨付きで示し、「全部推奨」
- 「レビューして」で reviewer と security-reviewer を動かし、指摘18件(S1 は案A・案B を提示)に「全部推奨で」
- 「マージして」(relay #11・API #17 → Web #15 → team-ops #17)

## 3. AIの出力

- **plan.md**:判断が要る点を7件(本文の暗号化、送信時点の宛先の保存、予約を見られる人、予約の公開の仕組み、監査ログ、リンクにする範囲、relay の7日後の削除)
- **ADR**:2件(お知らせの保存と宛先、公開と配信)
- **API**:お知らせの作成(今すぐ・予約)、届く人数、予約の一覧・編集・取り消し、毎分の予約の公開、自分宛ての一覧(50件ずつ)と表示。1,000人ずつに分けてアウトボックスへ。テストは473件
- **画面**:お知らせを書く、予約中の一覧・編集、一覧(続きを読み込む)と表示、ホームに新しい3件。テストは148件
- **relay**:受付から7日を過ぎた依頼を1時間ごとに1,000件ずつ消す。消されたあとの結果の記録は再試行しない
- **E2E**:学年宛てに送る → 該当の保護者と代表に1通ずつ届き、該当しない保護者には届かない → 予約して取り消す。送信元がログインのメールと同じこと

## 4. 人間が直したこと

コードを人間が直接書き換えた箇所はない。人間が直したのは判断。

- plan の7件とレビューの18件は、すべて推奨どおりに決めた
- S1(予約のあとに作成者が除名・役割変更されたら)は、AI が最初の PR で「判断してほしい点(未決)」として残していたもの。レビューで改めて案A・案B を示し、人間が案A(公開時に取り消して監査ログに理由を残す)に決めた。spec に AC-005-17 として足した

## 5. 判断(人間が決めたこと)

| 判断 | 内容 |
|---|---|
| 1 | タイトルと本文を暗号化して保存する |
| 2 | 送信時点の宛先をユーザーIDで保存し、除名されても残す(006 の母数) |
| 3 | 予約中のお知らせは作成者と代表・役員だけが見られる |
| 4 | スケジューラで毎分、行をロックして1件ずつ公開する |
| 5 | 送信・予約・編集・取り消し・公開を監査ログに残す(本文は残さない) |
| 6 | http:// と https:// の URL だけをリンクにする |
| 7 | relay は1時間ごとに、7日を過ぎた依頼を1,000件ずつ消す |
| レビュー | S1 案A(AC-005-17)、回数制限(AC-005-18)、一覧の続き(AC-005-19)、UTC で保存、日本時間で入力、書式文字の禁止、1件ごとの失敗の扱いほか18件すべて |

## 6. AIが間違えた点と学び

- **時刻の扱いが API と画面の両方でゆるかった(R1・R5)**
  - API は時差付きの値を UTC に直さずに保存し、画面は端末の時間帯で日時を読んでいた。テストは日本時間の環境でしか動かしていなかったので気づかなかった
  - 学び:日時は「どの時間帯で入力し、何で保存するか」を ADR に書いてから作る。テストは別の時間帯(TZ を変える)でも動かす
- **予約の公開を「作った時点の判断」のまま行う作りにしていた(S1)**
  - 予約のあとに作成者の権限がなくなる場合を、spec にないとして未決のまま残した。PR に書いたのはよかったが、plan の段階で判断として出すべきだった
  - 学び:時間差のある処理(予約・キュー)は、実行の時点で権限と前提を確かめ直す前提で plan を書く
- **濫用への備えがなかった(S2・S3)**
  - 全員宛ての送信を何度でもでき、本文に文字の向きを変える書式文字を入れられた。共通の送信元アドレスの評判を下げられる
  - 学び:外にメールを出す機能では、回数制限と見た目をごまかす文字の扱いを最初から spec に入れる
- **1件の失敗で予約の公開がすべて止まる作りだった(S4・R12)**
  - 学び:一括で処理するジョブは、1件ずつの失敗を分け、ログには ID だけを出す
- **編集画面の人数が、公開のときと違う人を送信者として数えていた(R6)**
  - 学び:同じ値を2か所で計算するときは、計算の部品を1つにまとめる
- **回数制限をルートの仕組みに置いたら、入力の誤りも数えていた**
  - 実装の途中でテストが落ちて気づいた。spec の「11件目のお知らせを作成する」に合わせ、作れた件数で数えるように変えた。判断が要る変更だったため、マージの前に人間に伝えた
  - 学び:spec の言葉(作成する/要求する)と、仕組みが数えるもの(成功/すべて)を合わせて確かめる
- **レビューの指摘の番号と内容を、作業の途中で正確に残していなかった**
  - 会話の途中経過がまとめられたため、資料だけで直した指摘の一部(R7)の番号と内容を、PR に正確に書けなかった。PR には番号を付けずに「そのほか資料の修正」と書いた
  - 学び:レビューの指摘は、示した時点で番号・内容・判断をファイル(tasks.md など)に書き残す
