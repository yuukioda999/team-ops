# notify-relay が3分止まっても、配信依頼は失われず、起動後に二重なく届いた

- 日付:2026-11-16
- 種類:障害訓練(spec 009 の AC-009-05)
- 判定:期待どおり
- 記録:https://github.com/yuukioda999/team-ops/actions/runs/43838162895

## 概要

お知らせの公開の30秒前に notify-relay を止め、公開の3分後に起動した。止まっている間、API は100件の配信依頼をアウトボックスに持ったまま送り直しを続け、起動の8秒後に3,000人全員へちょうど1通ずつ届いた。

## 影響

- 二重配信・取りこぼし:0
- 遅れ:最初の1通が予約の時刻から 184秒(止まっていた時間ぶん)
- 配信状況:最後はすべて「届いた」。API と notify-relay で食い違いなし

## 時系列(UTC)

| 時刻 | できごと |
|---|---|
| 09:19:30 | notify-relay を止める |
| 09:20:00 | 予約の時刻。100件のお知らせが公開され、アウトボックスに入る |
| 09:20〜09:23 | API の worker が送り直すたびに断られる(200回) |
| 09:23:01 | notify-relay を起動。この時点で送っていないアウトボックスは100件 |
| 09:23:04〜09:23:09 | 最初と最後の1通(起動から8秒) |

## どう気づいたか

- API のログに `notify-relay did not accept the outbox message; will retry` が 200件(WARNING)
- 送っていないアウトボックスの数を DB で数えられる(手順書に SQL を書いた)

## 原因

notify-relay が止まっていた。訓練で起こしたもの。

## どう戻したか

人は notify-relay を起動しただけ。送り直しは API が自動で行った(ADR-0002・0018)。

## 気になった点

起動してから送り始めるまでの時間は、送り直しの間隔の巡り合わせで変わる。この run では8秒だったが、同じ訓練の前の run(https://github.com/yuukioda999/team-ops/actions/runs/43836228968)では、起動から最後の1通まで 185秒かかった。送り直しの間隔は 30秒・1分・2分・5分・10分・30分と延びるので、長く止まるほど、起動してから送り始めるまで最大30分待つ。

## 次の手(人間の判断が要る)

- 起動したあと、待たずに送り直せる手段を用意するか(例:時刻の来ていない送り直しもすぐ積むコマンド、または送り直しの間隔の上限を短くする)。いまは手順書に「最大30分待つ」と書いた
