# notify-relay を送信の途中で強制終了しても取りこぼしはなく、二重に届いたのは最大47通だった

- 日付:2026-11-16
- 種類:障害訓練(spec 009 の AC-009-06)
- 判定:期待どおり
- 記録:https://github.com/yuukioda999/team-ops/actions/runs/43850003897(90日で消える)
- 確かめたコード:team-ops 9d1b2ae(PR のブランチの先頭)、team-ops-api ec04c8e(のちに作者だけを直して ecfbea5 と同じ中身)、notify-relay 7f60c9b(main)。このあと API は、送信ジョブの結果の書き方を直した(ffc3193 以降)。その版でも、同じ訓練を run 43856747950 で動かし、5種類とも期待どおりだった

## 概要

送信の途中で notify-relay を強制終了(SIGKILL)し、10秒後に起動した。3回とも取りこぼしはなかった。二重に届いたメールは 0・44・47通で、合否の基準(同時に送る数 50 以下、判断4)に収まった。ただし、上限の近くまで二重に届く回が多い。

## 影響

| ジョブ | 強制終了の時点で届いていた数 | sending のまま残った宛先 | 二重に届いた数 | 取りこぼし | notify-relay の起動から最後の1通 |
|---|---|---|---|---|---|
| relay-kill#1 | 870 | 0 | 0 | 0 | 49 秒 |
| relay-kill#2 | 885 | 179 | 44 | 0 | 53 秒 |
| relay-kill#3 | 1,257 | 290 | 47 | 0 | 50 秒 |

API の直しのあとの run 43856747950 でも、3回とも取りこぼしは0で、二重に届いたのは 48・49・47通だった(上限の50に近い)。

- 二重に届いた保護者には、同じお知らせのメールが2通届く
- 配信状況:最後はすべて「届いた」。宛先ごとに並べて食い違いなし
- relay-kill#1 は、送信の担当がどの宛先も取り出していない瞬間に止まったので、二重はなかった。この回は、強制終了の直前に受け付けの deadlock が2件出ていて(付録)、送信が止まりかけていた見込み

## どう気づいたか

- notify-relay の起動時のログに `requeued recipients interrupted by a previous stop`(WARN)が1件
- 本番では、メモリ不足なら `dmesg` に記録が残る
- 何通が二重に届いたかは、運用の手段では分からない(訓練では Mailpit で数えた)

## 原因

notify-relay は、送る直前に宛先を sending にし、送ったあとに結果を記録する(notify-relay の ADR-0002)。送ってから記録するまでの間に強制終了すると、起動時にその宛先を「まだ送っていない」として送り直すので、二重に届く。送信の担当は50で、1件ずつ「送る、記録する」を順に行うので、二重に届くのは最大50通になる。

二重に届いた数が50に近い回があった理由の見立ては2つあり、どちらかはまだ確かめていない。

- 送信先の Mailpit がすぐ応答するので、送信の時間のほとんどが「送ってから記録するまで」になる
- 記録は依頼の行をロックしてから宛先を1件ずつ書くので、同じ依頼の宛先を送り終えた担当が、記録の順番を待っていた

本物の SMTP サーバーは応答が遅いので、二重になる割合は下がる見込みだが、確かめていない。

## どう戻したか

人は起動しただけ(本番では `restart: unless-stopped` で自動で起動する)。

## 次の手

- (決定済み、2026-11-16)二重に届いたときに受け取った人が戸惑わないよう、お知らせの画面の本文の下に「まれに同じものが2通届くことがあります」と書く(AC-005-20、team-ops-web #23)。メールの本文に書く案は、本文の上限(notify-relay の受け付けが2,000文字、お知らせの本文も2,000文字まで)と重なるので、やめた
- Message-ID を宛先と依頼ごとに固定する案(同じ Message-ID のメールを1通にまとめるメールサービスもある)は、後で確かめる
- 二重の原因の見立てを確かめる:送信と記録にかかった時間をログで測る
