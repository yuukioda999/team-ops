# ADR-0025: 障害訓練の方法

- ステータス: 承認
- 日付: 2026-11-16
- 決定者: 小田 裕貴
- 関連: ADR-0002、ADR-0018、ADR-0019、ADR-0023、notify-relay の ADR-0002(二重送信が起こりうる時間)、specs/009-chaos-drill(判断1〜6)

## コンテキスト

- 設計で「notify-relay が止まっても依頼を保持し、復旧後に二重なく送る」「SMTP の一時エラーは再送、恒久エラーは失敗として記録」「結果の webhook が届かなくても最後にはそろう」と約束している(ADR-0002・0018・0019、notify-relay の AC-R001-10〜20)
- これらは単体と結合のテストで確かめているが、すべてのサービスを動かした状態で、実際に止めて確かめたことはない
- notify-relay は、強制終了のときだけ、送信中だったメールが二重に届きうることを受け入れている(notify-relay の ADR-0002)
- 負荷試験(ADR-0023)で、試験データの作成と GitHub Actions での実行の道具がそろっている

## 検討した選択肢

| 論点 | 採用した案 | 退けた案 |
|---|---|---|
| 動かす場所 | **GitHub Actions。手元では同じスクリプトを動かせる** | 手元で人間が `make` を順に打つ(手順と時刻がずれ、根拠が残らない) |
| 規模 | **100チーム(3,000通)** | 1,000チーム(再送の待ちと重なって長くなる) |
| SMTP の一時エラー | **配信の始まりから2分だけ、30% に 451 を返す** | 訓練の間ずっと返し、再送の間隔を設定で短くする(relay に訓練用の設定が要る) |
| 強制終了の合否 | **取りこぼしは0。二重に届いた数は、止めた時に送信中だった数以下なら設計どおり** | 二重配信も0(relay の設計で受け入れた範囲を否定する) |
| 振り返り | **訓練ごとに1つのファイル。雛形を置く** | 5つの訓練を1つのファイルにまとめる |
| 回数 | **各1回。強制終了だけ3回** | すべて3回 |

## 決定

- `chaos/` に、訓練の compose の設定(`compose.chaos.yaml`)、訓練を動かすスクリプト(`drill.sh`)、結果をまとめるスクリプト(`report.py`)を置く
- `.github/workflows/chaos.yml` で、5つの訓練を並べて動かす。手で実行するときは訓練の種類と回数を選べる
  - 道具を変えた PR でも、同じ規模で自動で動かす。手で実行するワークフローは main にあるものしか動かせないため
  - 負荷試験と違い、PR と手で実行する回で規模が同じなので、PR の回も結果として使ってよい(run の URL を残す)
- メールの数えは Mailpit の API で宛先ごとに行う。Mailpit が古いメールを消さないように、訓練では件数の上限を外す
- 配信状況の照らし合わせは、API の `notice_recipients` と notify-relay の `delivery_recipients` を、宛先(`user_<ID>`)とお知らせの ID でつないで比べる。訓練の道具が両方のスキーマを読むのは、サービスの間の約束(ADR-0004)とは別に、結果を確かめるためだけに行う
- 振り返りは `docs/postmortems/` に、人間が結果を確かめてから書く。期待と違う結果は、直し方を選択肢と推奨で示して人間が決める

## 結果

良くなること:

- 設計の約束を、止めて確かめた記録で示せる。面接で「どこまでなら二重に届きうるか」を数字で説明できる
- 同じ障害を何度でも起こせるので、直したあとに同じ訓練で確かめられる

悪くなること・受け入れるコスト:

- 開発用の構成(`php artisan serve`)で動かすので、本番の FrankenPHP とは止まり方や起動の時間が違う
- 監視とアラートはまだないので、「どう気づいたか」はログと配信状況で記録する。アラートは次の手として扱う

## 見直す条件

- 訓練の結果が回によって変わり、1回では合否を決められない場合(回数を増やす)
- 本番の構成(FrankenPHP、Caddy)でしか起きない障害を確かめる必要が出た場合
