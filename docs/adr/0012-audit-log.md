# ADR-0012: 監査ログは 002 で最小限の仕組みを作る

- ステータス: 承認
- 日付: 2026-11-07
- 決定者: 小田 裕貴
- 関連: ADR-0003、specs/002-invitation(判断8)、specs/003-roster(AC-003-11)、specs/004-roles-and-permissions

## コンテキスト

- 002 の補足に「招待リンクの発行・無効化・承認・却下は監査ログに残す」とある。003 の名簿の閲覧、004 の役割変更・除名も監査ログに残す
- 監査ログの閲覧は代表だけ(004 の権限表)
- 監査ログ自体に個人情報を書くと、守る情報が増える(ADR-0003)

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **002 で表と記録の部品だけを作る。閲覧画面は 004** | **002 の操作を最初から記録できる。作る量は小さい** |
| B | 003 でまとめて作る | 002 の操作が記録されない期間ができる |

## 決定

案Aを採用する。

- 表 audit_logs:id、team_id、actor_user_id(操作した人)、action(操作の種類)、subject_type・subject_id(対象)、details(JSON)、created_at
- details には個人情報(表示名・メールアドレス・ひとこと・名簿の項目)を入れない。ID と、役割などの区分だけを入れる
  - 例外:名簿の閲覧の記録には、絞り込みの条件(学年・背番号)を残す(ADR-0013、2026-11-07 追記)
- 記録は業務処理と同じトランザクションで行う(処理が取り消されたら記録も残らない)
- 記録の部品は Support/Audit に置き、UseCase から呼ぶ
- 保存期間は、ほかの個人情報の扱い(003 以降)と合わせて決める。002 では消さない

## 結果

良くなること:

- 002〜004 の操作を、同じ形で記録できる
- 監査ログを読まれても、個人情報は分からない

悪くなること・受け入れるコスト:

- 「誰が」を人の名前で見るには、閲覧時にユーザーの表と突き合わせる必要がある(004 の閲覧画面で行う)

## 見直す条件

- 監査ログの件数が増え、別の保存先(ログ基盤など)が必要になった場合
