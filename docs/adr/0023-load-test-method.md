# ADR-0023: 負荷試験の方法

- ステータス: 承認
- 日付: 2026-11-13
- 決定者: 小田 裕貴
- 関連: ADR-0002、ADR-0003、ADR-0004、ADR-0019、specs/008-load-test(判断1〜6)

## コンテキスト

- 要件の目標は、30万通(1万チーム × 30人)を10分以内に送り終えることと、主要な API の p95 が 300ms 以下であること(project-brief.md)
- ADR-0002 と ADR-0004 には「負荷試験で確かめる」とした点がある(Go に切り出した効果、同じ MySQL を使う影響)
- 要件では「自分の PC でモック相手に実行し、結果をリポジトリに残す」としていた。ただし、直す前と後を比べるには、毎回同じ性能のマシンで測る必要がある
- 名前とメールアドレスは暗号化とブラインドインデックスで保存している(ADR-0003)。試験のデータも Laravel の処理を通して作る必要がある

## 検討した選択肢

| 論点 | 採用した案 | 退けた案 |
|---|---|---|
| 実行する場所 | **GitHub Actions のマシンで手で実行し、結果をリポジトリに残す** | 自分の PC(性能が毎回同じとは限らず、直す前と後を比べにくい) |
| メールの送り先 | **受け取って捨てるだけの SMTP サーバー(受け取り役)を Go で作る。1通ごとの待ち時間を指定できる** | Mailpit(30万通を溜めると Mailpit が先に詰まる) |
| 試験の種類 | **relay 単体、全体(予約の公開から送信まで)、配信の最中の API の3つ** | 全体だけ(どこが詰まっているかを切り分けられない) |
| 試験のデータ | **API に試験用の artisan コマンドを作り、行をまとめて insert する。`APP_ENV` が local・testing・loadtest 以外では止まる** | 公開 API で作る(1万チームに数時間かかる)/ SQL で直接作る(暗号化できない) |
| API の試験のログイン | **データを作るコマンドが試験用のセッションを作り、Cookie を k6 に渡す** | k6 がマジックリンクでログインする(リンクの読み出しの仕組みが要り、回数制限に当たる) |
| 受け取り役の待ち時間 | **1通 50ms を標準にし、比較のため 0ms でも1回測る** | 0ms だけ(本物の SMTP より楽な条件になる) |
| CPU とメモリ | **目標は制限なしで測る。参考に、デモの VPS と同じ制限(3コア・2GB)でも全体の試験を1回測る** | 制限ありだけ(目標の規模は 2GB の VPS 1台を想定していない) |
| 置き場所 | **team-ops の `loadtest/`。受け取り役は標準ライブラリだけで作る** | notify-relay のリポジトリ(relay は業務アプリから独立した OSS で、試験の構成は team-ops の領分) |

## 決定

- `loadtest/` に、受け取り役(Go)、k6 のシナリオ、試験用の compose の設定、結果を置く
- `.github/workflows/loadtest.yml` を手で実行する。規模(チーム数)、試験の種類、受け取り役の待ち時間、CPU とメモリの制限を選べる。結果は成果物(artifact)として残し、人間の確認のあとに `loadtest/results/` へコミットする
- API と notify-relay は本番と同じイメージで動かす(開発用の `php artisan serve` ではなく FrankenPHP)
- API の `loadtest:seed` は、試験用のチーム・利用者・予約のお知らせを作る。宛先はすべて `.invalid` で、外には出ない
- 目標を満たせなかったときも、数字をよく見せるために条件を変えない。数字と原因と次の手を記録する
- 直し方はそのたびに選択肢と推奨を示し、人間が決める。設計を変える場合は ADR を書く

## 結果

良くなること:

- 目標が主張ではなく、測った数字で示せる
- どの段階が詰まっているかを、段階ごとの時刻で切り分けられる
- 直した効果を、同じ条件で確かめられる

悪くなること・受け入れるコスト:

- GitHub Actions のマシンの数字は、本番のサーバーの性能を表さない(README に明記する)
- API に試験用のコマンドが入る(本番の環境では動かない)

## 見直す条件

- GitHub Actions のマシンで、試験の結果が回によって大きく揺れる場合
- 本物の送信サービスを選ぶ段階になった場合(その上限での試験を足す)
