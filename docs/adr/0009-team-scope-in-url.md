# ADR-0009: 操作対象のチームはURLのチームIDで指定する

- ステータス: 承認
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: ADR-0001、specs/README.md(AC-000-01)、specs/001-account-and-team(AC-001-13)

## コンテキスト

- 1人のユーザーが複数のチームに所属できる(きょうだいが別のチームにいる保護者など)。AC-001-13 で、選んだチームのデータだけを扱うと決めている
- 他チームのデータは404を返し、存在の有無も分からないようにする(AC-000-01)。この検査を漏れなくかけたい
- 同じ人が、2つのタブで別々のチームを開くことがありうる

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **APIのURLにチームIDを入れる(`/api/teams/{team}/...`)** | **リクエストごとに対象が明確。所属の検査をルートで一括してかけられる。タブごとに別のチームを扱える** |
| B | 選択中のチームをサーバーのセッションに覚えておく | URLは短くなるが、タブ間で選択が混ざる。対象チームがリクエストから見えず、テストもしにくい |

## 決定

案Aを採用する。

- チームに属するAPIは、すべて `/api/teams/{team}/...` の下に置く
- `{team}` は、ログイン中のユーザーが所属するチームだけから探す。所属していないチームは、存在していても404にする。この処理をルートモデルバインディングにまとめ、各Controllerで書かない
- チームの中のデータ(名簿・お知らせなど)を探すときも、必ずそのチームIDで絞り込む
- チームIDは連番ではなくULIDにする。URLに出るため、チーム数などを推測させない
- Web の画面も `/teams/:teamId/...` とし、URLを共有・ブックマークしても同じチームが開く

## 結果

良くなること:

- 他チームのデータを返さない検査が1か所にまとまり、Feature テスト(tests/Tenancy)で網羅的に確かめられる
- タブごとに別のチームを開いても混ざらない

悪くなること・受け入れるコスト:

- URLが長くなる
- 新しいAPIを `/api/teams/{team}` の外に置いてしまうと検査が漏れる。レビューと、ルート一覧を検査するテストで防ぐ

## 見直す条件

- チームをまたいで集計する画面(複数チームの予定を一覧するなど)が必要になった場合
