# ADR-0010: 招待リンクの持ち方と、ログイン後に元の画面へ戻す方法

- ステータス: 承認
- 日付: 2026-11-07
- 決定者: 小田 裕貴
- 関連: ADR-0003、ADR-0008、specs/002-invitation(判断1・2・9)、specs/001-account-and-team(AC-001-19)

## コンテキスト

- 招待リンクは、代表・役員がチームの LINE グループに1つ貼り、7日間使い続けるもの(AC-002-01)。あとから同じリンクや QR コードを見せ直したい場面がある
- 未ログインの保護者は、招待リンク → ログイン用メール → ログイン → 参加申請、と進む(AC-002-05)。ログイン用メールのリンクは、メールアプリの中のブラウザや新しいタブで開くことが多い
- 001 では、ログイン後に戻る先を sessionStorage に持っていた。同じタブでしか戻れない(001 最終レビューの J)

## 検討した選択肢

### 招待リンクのトークン

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **照合用の SHA-256 と、暗号化したトークンの両方を持つ** | **代表・役員が同じリンクと QR を何度でも表示できる。DB が漏れても、鍵がなければトークンは分からない** |
| B | SHA-256 だけを持つ(ログイン用と同じ) | 見せ直すには発行し直すしかなく、LINE に貼ったリンクが無効になる |

### ログイン後の戻り先

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **ログイン用リンクの要求に戻り先を付け、API がログイン用のトークンと一緒に保存して、ログインの応答で返す** | **別のアプリやブラウザで開いても戻れる。メールの URL は短いまま** |
| B | 戻れないことを受け入れ、招待リンクを開き直すよう案内する | 保護者が一番多く通る道で手間が増える |
| C | 戻り先を localStorage に持つ | 同じブラウザの別タブでは戻れるが、メールアプリの中のブラウザでは戻れない |

### QR コード

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **画面(ブラウザ)で、表示中の URL から作る(npm の qrcode)** | **トークンを含む画像を API の応答に増やさない** |
| B | API で SVG を作る | サーバーで作る理由がない |

## 決定

すべて案Aを採用する。

- 招待リンクのトークンは32バイトの乱数。照合には SHA-256、表示し直すために暗号化(APP_KEY)したトークンを持つ。表示できるのは、そのチームの代表・役員だけ
- 招待リンクは Web の `/join?token=...`。ログイン用リンクと同じく、画面が読んだらすぐ URL から消し、nginx のログに残さない(001 の D7)
- 期限切れ・無効化・存在しないリンクは、区別せず同じ応答にする
- ログイン用リンクの要求に `return_to` を付けられる。受け付けるのは決まった形のパスだけ(`/join?token=` と、メール変更の確認 `/settings/email/verify?token=`)。外部の URL や、それ以外のパスは無視する
- `return_to` はログイン用のトークンと一緒に保存し、ログイン用メールのリンクには含めない。リンクを使ってログインした応答で返し、画面がそこへ進む。メールの URL を短く保ち、戻り先の中のトークンがメールの URL に二重に入らないようにする

## 結果

良くなること:

- 保護者は、ログイン用メールをどのアプリで開いても、ログイン後に申請画面へ進める
- メール変更の確認(D5)も、別のタブで開いて戻れるようになる
- 代表・役員は、同じ招待リンクと QR をいつでも表示できる

悪くなること・受け入れるコスト:

- 招待リンクのトークンを復号できる形で持つ。鍵(APP_KEY)の管理が前提になる(公開済みの鍵は本番で拒否する、001 最終レビューの G)
- ログイン用トークンの行に、戻り先を1列足す

## 見直す条件

- 招待リンクの見せ直しが不要になった場合(個別招待に切り替えるなど)は、ハッシュだけに戻す
