# ADR-0022: デモ環境のサーバーと公開の方法

- ステータス: 承認
- 日付: 2026-11-08
- 決定者: 小田 裕貴
- 関連: ADR-0002、ADR-0004、ADR-0021、specs/001-account-and-team(T35)、specs/007-demo-mode

## コンテキスト

- 面接官などの訪問者が、デモモード(ADR-0021)で全機能を試せるように、インターネットに公開する
- ポートフォリオなのでアクセスは少ない。ただし、開いたときに落ちていないことを最優先にする
- 費用は月額固定にする。従量課金で思わぬ請求が来る構成は避ける
- 外部にメールは送らない。デモのメールは Mailpit が受け止め、画面の「送信されたメール」で見せる(ADR-0021)
- 開発環境は compose.yaml で、API は `php artisan serve` で動かしている。本番には向かない(T35)

## 検討した選択肢

| 論点 | 採用した案 | 退けた案 |
|---|---|---|
| サーバー | **さくらのVPS 2GB を1台、まず月払い** | 1GB(MySQL・PHP・キュー・定期処理・notify-relay・Mailpit・nginx が常に動き、合計1.2〜1.5GB。足りなくなると MySQL が強制終了される)/ マネージドのクラウド(従量課金) |
| 画面の配信 | **VPS の nginx(画面のイメージ)から配る** | Cloudflare Pages(API と別のドメインになり、Cookie と CORS の設定が増える) |
| ドメイン | **`demo.freie.jp`** | 新しいドメインを取る |
| API のサーバー | **FrankenPHP**(コンテナ1つで HTTP を受ける。画面の nginx は今のまま `/api` を転送する) | php-fpm と nginx(API の中に nginx がもう1つ要るか、画面の nginx が API の中身を知る形になる) |
| HTTPS | **Caddy を一番前に置き、Let's Encrypt の取得と更新を任せる** | nginx と certbot(更新を cron で回す)/ Cloudflare を前に置く(DNS の移管が要る) |
| イメージの作り方 | **GitHub Actions で作り、GHCR に置く** | サーバーの上でビルドする(メモリが足りず、時間もかかる) |
| デプロイ | **最初はサーバー上の `deploy.sh` を人が実行する** | GitHub Actions が SSH で入って自動で更新する(サーバーに入れる鍵を GitHub に預けることになる。慣れたら見直す) |
| バックアップ | **毎日 DB を書き出し、サーバー上に7日分残す。戻す手順を手順書に書き、一度実際に戻して確かめる** | 外部のストレージにも置く(デモのデータは24時間で消える架空のものなので、今は費用に見合わない) |
| 監視 | **Grafana Cloud の無料枠にトレースとログを送る(今の OpenTelemetry をそのまま使う)。外から5分ごとにトップ画面を確かめる** | サーバーの中に Grafana を置く(メモリを使い、サーバーが落ちると監視も落ちる) |

## 決定

- サーバー:さくらのVPS 2GB、Ubuntu 24.04 LTS。まず月払いで始める
- 公開する URL:`https://demo.freie.jp`。外から受けるのは 80・443(Caddy)と SSH だけ
- 構成(1台の Docker Compose、`compose.prod.yaml`)
  - Caddy:HTTPS を終端し、画面の nginx に転送する
  - web:画面のイメージ(nginx)。画面を配り、`/api` を API に転送する
  - api:FrankenPHP のイメージ(T35)。キューの処理と定期処理も同じイメージで別のコンテナとして動かす
  - notify-relay、MySQL、Mailpit
  - Mailpit の画面と SMTP、MySQL は外に出さない
- デモモードを有効にする(`DEMO_MODE=true`)。外部にメールは送らない
- 秘密情報(アプリの鍵、DB のパスワード、notify-relay の署名鍵など)はサーバー上の `.env` だけに置き、Git には入れない
- イメージは main にマージされたときに GitHub Actions で作り、GHCR に置く。タグはコミットのハッシュ
- デプロイは、サーバーで `deploy.sh <タグ>` を実行する。イメージを取ってきて、マイグレーションを流し、コンテナを入れ替える。前のタグを指定すれば戻せる
- 手順書(docs/runbook/)に、初期設定・デプロイ・戻し方・バックアップと戻し方・証明書・監視を書く

## 結果

良くなること:

- 月額が固定で、思わぬ請求が来ない
- 開発環境と同じ Compose の考え方で動くので、手元で再現しやすい
- 画面と API が同じドメインなので、Cookie と CORS の設定が開発環境と同じで済む

悪くなること・受け入れるコスト:

- サーバーが1台なので、サーバーやさくらの障害のときはデモが止まる
- OS の更新やバックアップの確認は自分で行う
- デプロイは手作業なので、手順書どおりに行う必要がある

## 見直す条件

- メモリの使用量が常に8割を超える、またはデモの作成が遅くなった場合
- 実在の利用者に使ってもらう段階になった場合(メールの送信サービス、外部へのバックアップ、デプロイの自動化を決め直す)
