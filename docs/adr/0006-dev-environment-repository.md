# ADR-0006: 開発環境とシステム全体の資料を team-ops リポジトリに分ける

- ステータス: 承認
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: ADR-0001

## コンテキスト

- サービスは3つ(team-ops-api / team-ops-web / notify-relay)で、リポジトリも分かれている
- ローカルでは、3つのリポジトリを同じ階層に置き、1つの docker compose で全環境(3サービス、MySQL、Mailpit、Grafana)を起動したい。各サービスはソースからビルドし、コードの変更をすぐ反映したい
- 要件・全体のADR・機能仕様・負荷試験・障害訓練は、複数のサービスにまたがる
- 面接官が最初に見る「入口」を1か所にしたい

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | team-ops-api に compose と全体の資料を置く | リポジトリは増えないが、APIのリポジトリが他の2つの起動方法や全体の資料まで抱え、役割があいまいになる |
| **B** | **開発環境と全体の資料を持つ team-ops リポジトリを新設する** | **役割が明確になり、入口が1か所になる。リポジトリが1つ増える** |
| C | 4つ目を作らず、各リポジトリに compose を置く | 全環境を一括で起動できない |

## 決定

案Bを採用する。

- team-ops に、compose.yaml・Makefile・環境の設定と、システム全体の資料(要件、全体のADR、機能仕様、運用、負荷試験、障害訓練)を置く
- 4つのリポジトリを同じ階層に置く前提とし、`make setup` で残り3つを隣に clone する
- サービス固有の資料(API仕様、サービス内部の設計判断)は、各サービスのリポジトリに置く
- notify-relay はOSSとして単独で読めるよう、自分のADR・仕様・OpenAPIを持ち続ける

## 結果

良くなること:

- 面接官は team-ops を開けば、全体像・資料・起動方法がそろう
- 各サービスのリポジトリは、自分の責務だけに集中できる

悪くなること・受け入れるコスト:

- リポジトリが4つになる
- 機能仕様(team-ops)と実装(各サービス)が別のリポジトリになる。PRの説明に対応する仕様へのリンクを必ず書く

## 見直す条件

- リポジトリ間の行き来が開発の負担になった場合(モノレポへの統合を検討する)
