# ADR-0026: トレースとメトリクスの方法

- ステータス: 承認
- 日付: 2026-11-19
- 決定者: 小田 裕貴
- 関連: ADR-0002(サービスをまたいだトレースID)、ADR-0003(個人情報)、ADR-0021(デモの指標)、ADR-0022(デモ環境の監視)、ADR-0023(負荷試験)、specs/010-observability(判断1〜7)

## コンテキスト

- 要件で「サービスをまたいだトレースIDで、1通の通知を配信先まで追跡できること」「ローカルにも Grafana 一式(トレース・メトリクス・ログ)を立て、デモ環境と同じダッシュボードで確認できること」「SLO、監視・アラート設計」を求めている
- いまは、ローカルの compose に Grafana 一式(otel-lgtm)があるだけで、API も notify-relay もトレースとメトリクスを出していない。デモ環境はログと、サーバーの CPU・メモリ・ディスクだけを Grafana Cloud に送っている(ADR-0022)
- 障害訓練(spec 009)の振り返りで、一時エラーが続いても気づきにくいこと、アラートがないことを次の手にした

## 検討した選択肢

| 論点 | 採用した案 | 退けた案 |
|---|---|---|
| API の計装 | **PHP の拡張(ext-opentelemetry)と Laravel の自動計装。足りない所だけ手で書く。送る前に個人情報を伏せる** | SDK だけで手で書く(書く量が多く、DB の時間などが見えない) |
| notify-relay の計装 | **OpenTelemetry の Go SDK(トレースとメトリクス、OTLP の HTTP)** | メトリクスだけ Prometheus のクライアントで出す(1本のトレースでたどれない) |
| デモ環境での送り方 | **アプリは同じサーバーの Alloy に OTLP で送り、Alloy が Grafana Cloud へ送る** | アプリから直接 Grafana Cloud へ送る(鍵が3か所に散る) |
| ダッシュボードとアラート | **定義のファイルをリポジトリに置き、ローカルとデモ環境で同じものを使う。通知はメールで、宛先は Grafana Cloud の設定にだけ置く** | 画面で作って書き出す(どちらが正しいかがずれる) |
| サンプリング | **ローカルとデモ環境は全部残す。負荷試験では既定で止める** | どこでも一部だけ残す(「この1通」を追えないことがある) |
| CI での確かめ方 | **smoke で otel-lgtm も起動し、トレースとメトリクスが届いたことを問い合わせて確かめる。障害訓練で、対応するアラートが発火することを確かめる** | 単体テストで作ることだけを確かめる(届くかは分からない) |
| SLO と監視の設計の置き場所 | **docs/ops/(要件の置き場所どおり)。戻し方は docs/runbook/** | すべて monitoring.md に足す |

## 決定

- 送るのは OpenTelemetry の形(OTLP の HTTP)。送り先は `OTEL_EXPORTER_OTLP_ENDPOINT` で決める。ローカルは otel-lgtm、デモ環境は Alloy
- サービス名は `team-ops-api`(API・worker・scheduler は同じ名前で、`service.instance.id` などで分けない。プロセスの種類は属性で分ける)と `notify-relay`
- トレースの受け渡しは W3C Trace Context(`traceparent`)。API から notify-relay への依頼、notify-relay から API への webhook の両方で付ける。アウトボックスに traceparent を保存し、送り直しても同じトレースにつなぐ
- 個人情報は、送る前の処理で伏せる。URL のクエリ、DB の文の値、HTTP のヘッダー(Cookie・Authorization)、例外のメッセージは送らない。メトリクスのラベルにチームID・利用者ID・宛先を使わない
- 負荷試験(ADR-0023)では `OTEL_SDK_DISABLED=true` を既定にし、入れるかは設定で選べるようにする

## 結果

良くなること:

- 「このお知らせが届かない」に、1本のトレースで答えられる。配信の遅れや失敗の増加に、アラートで気づける
- ローカルで見たダッシュボードを、そのままデモ環境でも見られる

悪くなること・受け入れるコスト:

- API のイメージに PHP の拡張が増え、notify-relay の依存が十数個増える(notify-relay の ADR に理由を書く)
- 計装は処理を少し遅くする。負荷試験の数字とは、止めた状態で比べる
- 自動計装は、ライブラリが付ける属性に個人情報が入りうる。伏せる処理を単体テストで確かめ、security-reviewer を必ず通す

## 見直す条件

- Grafana Cloud の無料枠を超えそうになったとき(サンプリングを入れる)
- 計装で、主要 API の p95 が目標(300ms)を外れるほど遅くなったとき
